## 1. Motivation (what is broken today)

1. **Sandwich bug in `d548d86`'s reorder.** A personal user whose own rules straddle a locked
   rule (`[mine-A, locked, mine-B]`) can submit a legal permutation of their own IDs that lands
   `mine-B` *before* the locked rule, outrunning it in first-match-wins evaluation. The check
   validates set membership, not boundary crossings.
2. **Users can edit instance-wide rules.** `RuleService::canUserMutateRule()` accepts
   scope-`all` rules and `savePersonalRule()` preserves `userScope='all'` on edit, so a
   non-admin can change the path/mode/algos of any non-enforced global rule for every user.
3. **The priority inversion.** Original spec: higher order value = higher priority, global rule
   = priority 0 = last resort. Implementation: global rule at slot 0 of an array evaluated
   front-to-first-match — the `**` catch-all matches everything first, so **every additional
   rule is dead** while it is enabled. (`RuleService`'s docblock "first = highest priority"
   codified the inversion.)

**Acknowledged behaviour change (user-confirmed):** fixing #3 makes every additional rule go
live on any instance with an enabled global rule. The app is unpublished; no external
migration path is required.

## 2. The band model

Rules are stored in **one JSON array** (IAppConfig key `rule_definitions`, unchanged) that is
**always maintained in band order**. Evaluation walks it top to bottom; **first match wins**;
the first matching rule is the file's verdict carrier (see §4). Seven bands, user-confirmed:

| Band | Contents | Authored by | Ordered by | Non-admin user sees |
|------|----------|-------------|------------|---------------------|
| 1 | user-scoped, `admin_enforced` | admin | admin | read-only (own uid only) |
| 2 | group-scoped, `admin_enforced` | admin | admin | read-only (own groups only) |
| 3 | global, `admin_enforced` | admin | admin | read-only |
| 4 | user-scoped, not enforced | user **or admin** | the owning user (admin may too) | **editable (own uid only)** |
| 5 | group-scoped, not enforced | admin | admin | read-only (own groups only) |
| 6 | global, not enforced | admin | admin | read-only |
| 7 | the single pinned `**` global default | admin | (single rule) | read-only |

Mnemonic: *enforced beats unenforced; within each half, specific beats general; the catch-all
is last.* The specific-first enforced half is deliberate (user decision #1): it lets an admin
express "enforce sha256 everywhere, sha512 for alice" — under general-first the alice rule
would be silently dead. All enforced rules are admin-authored, so this costs nothing in safety.

### 2.1 Scope encoding

`userScope` keeps its field name and string type (zero migration):

| Value | Meaning |
|-------|---------|
| `'all'` | global |
| `'group:<gid>'` | Nextcloud group `<gid>` (NC user IDs cannot contain `:`; unambiguous) |
| anything else | user ID |

Helper (new, in `RuleService`): `scopeKind(string $userScope): 'global'|'group'|'user'` and
`scopeGroupId(string $userScope): ?string`.

### 2.2 Band derivation — derived, never stored

```
band(rule):
    if rule.pinned            → 7
    kind = scopeKind(rule.userScope)
    if rule.admin_enforced:   user → 1, group → 2, global → 3
    else:                     user → 4, group → 5, global → 6
```

`band` never appears in the stored JSON. API responses include it as a computed annotation.
A rule whose `admin_enforced` or `userScope` changes on update **moves to the end of its new
band** (explicit rule — do not preserve numeric position across bands, it is meaningless there).
`ruleAdd()` appends the new rule **at the end of its derived band**, not at the end of the array.

### 2.3 Storage invariant + migration

**Invariant:** after every mutation (`add`/`update`/`delete`/`toggle`/`reorder`/migration) the
stored array is stable-sorted by `band()`. Within a band, array order is the authoritative
priority order. Implement one private `RuleService::saveRules(array $rules)` that applies the
stable band sort before persisting; route every existing `setValueString(...rule_definitions...)`
call through it.

**Migration** (one-time, idempotent): a repair step `lib/Migration/RepairBandOrder.php`
implementing `OCP\Migration\IRepairStep`, registered in `appinfo/info.xml` under
`<repair-steps><post-migration>`:
1. Load the array. If empty → done.
2. If no rule has `pinned === true`: set `pinned = true` on the **slot-0** rule *iff* its
   `userScope === 'all'` (that is today's global rule by convention). If slot 0 is not
   global-scoped, set `pinned` on the first `userScope === 'all'` rule instead; if none exists,
   pin nothing (the default is simply absent — the admin UI's "Create Global Rule" path covers
   creation, and creates it with `pinned: true` from now on).
3. Stable-sort by `band()`; persist via `saveRules()`.
4. Idempotency: running again is a no-op (a `pinned` rule already exists; sort is stable).

### 2.4 Who may do what (authorization matrix)

- **Admin:** create/edit/delete/toggle any rule, any scope, any enforced flag; reorder within
  any band (including any single user's band-4 segment); may not delete the pinned rule, may
  not move any rule across a band except via flag/scope change, may not unpin/re-pin via API.
- **Non-admin with rule-editing permission** (`PermissionService::canUserEditRules()`):
  create/edit/delete/toggle/reorder **only** rules with `userScope === own uid`, not enforced,
  not pinned (⇒ band 4), and only where `isPathWritableByUser()` holds — this **tightens**
  `canUserMutateRule()`, closing motivation #2. Scope and `admin_enforced` are never taken
  from a non-admin payload: scope is forced to the caller's uid, enforced to false.
- Admin-authored band-4 rules are the owning user's to edit/reorder/delete (user decision #3 —
  "admin gives support"). Authorship confers nothing; the enforced flag is the only lock.
- **Band-4 note:** rules of different users never compete (scope filter at match time), so only
  *same-owner relative order* is meaningful there. Reorder of band 4 always targets one owner's
  segment.

### 2.5 The pinned global default (band 7)

Single, undeletable, drag-immovable, scope and path pinned server-side (`'all'` / `'**'`), and
**disable-able via the normal `enabled` toggle** (user decision #4; the empty-algos alternative
was rejected — it would overload the "at least one algorithm" validation). Marked `pinned: true`
(assigned by migration; set on creation via the global-rule creation path).

### 2.6 Priority display: `<band>.<order>`, 1 = highest

User decision #5, **reverting the old numbering spec**: 1 is now the highest priority. The
table renders in evaluation order, top wins; each row shows `<band>.<position-within-band>`
(1-based): `1.1` beats everything; the pinned default is `7.1` at the bottom. Numbers ascend
down the page. No standalone "Priority" integers anywhere anymore.

## 3. Verdict types: `include | ignore | exclude`

New rule field `type` (absent ⇒ `'include'`, zero migration). One terminal verdict per file —
the first matching rule decides; there is **no** fall-through and **no** per-dimension
resolution (both explicitly rejected; see §8 Reserved).

| Type | Automatic pipeline (listeners, background jobs, `evaluateRules`) | On-demand (sidebar/API recalc, CLI generate) | algos/mode |
|------|------------------------------------------------------------------|----------------------------------------------|------------|
| `include` | ✔ per algos+mode | ✔ (subject to permissions) | required |
| `ignore` | ✘ | ✔ | not stored |
| `exclude` | ✘ | ✘ — rejected with a clear error naming the rule | not stored |

Authority comes from band position, uniformly: an *enforced* exclude (bands 1–3) is an
unoverridable mandate; a *user* exclude/ignore (band 4) opts that user's files out of the
defaults below (legitimate by definition); a *default* exclude (bands 5–6) is overridable by a
user include in band 4. An enforced `ignore` is coherent: "the system stays off this path;
users may hash by hand."

**Enforcement points** (all new except the first):
1. **Listeners** (`FileListener`, 3 call sites): already fetch the first matching rule; add
   `type !== 'include'` ⇒ do nothing.
2. **Batch** (`evaluateRules()`/`processRule()`): a non-include rule *claims* its matching
   files into the existing exclusion set and marks nothing — the exclusion-set mechanism
   already exists; non-include rules feed it.
3. **Manual recalc** (`ChecksumApi::recalcHash()`, reached by sidebar, `/api/v1/.../recalc`):
   look up `findFirstMatchingRule($path, $ownerUid)`; if the verdict is `exclude` → error
   ("Hashing is excluded for this path by rule <id>"), surfaced as **403** by the controllers.
   `ignore`, `include`, or no match ⇒ allowed. Add a `RuleService` dependency to `ChecksumApi`
   if absent. This is the same location Feature 6's `manual_recalc` permission check will later
   join (who × where; two orthogonal gates).
4. **CLI** `file-checksum-search:generate`: skip files whose verdict is `exclude` (report a
   skipped count); `ignore` does **not** block the CLI (it is deliberate/manual in nature).
   `rebuild` is untouched (index-only, computes nothing).

**Rationale recorded:** exclude ≠ "include with empty algos" (validation conflict, hides
intent, silent about the manual dimension). The metered-external-storage case is `exclude`.

**OPEN — decision #9, confirm before Block 3 executes:** existing hashes of files newly covered
by `ignore`/`exclude`. **Recommendation: stop maintaining, do not purge** — least destructive,
reversible, purge remains available via CLI. Blocks nothing before Block 3.

## 4. REST API

Everything below `/apps/file_checksum_search/`. All new endpoints become documented contract in
`docs/api-v1.md` + `docs/api-v1-openapi.yaml`. None are rate-limited (cheap config ops —
document as such). Mutations keep CSRF protection (no `#[NoCSRFRequired]`); GETs get
`#[NoCSRFRequired]` per existing convention. `/api/v1/` has no external consumers; the contract
may change freely.

### 4.1 Rules — one resource, capability decides, not the URL

`#[NoAdminRequired]` on all; capability enforced in the service layer (§2.4). This kills the
admin-page/personal-page controller split: an admin-group member gets admin capability from any
surface.

```
GET    /api/v1/rules
       → { success, rules: [ { id, type, userScope, path, algos?, mode?, enabled,
             admin_enforced, pinned, band, position, priority: "4.2", canEdit } ... ],
           canCreate, supportedAlgos,
           availableUsers?, availableGroups? }        # pickers; admin callers only
       Admin: all rules. Non-admin: rules applicable to them — scope all; scope group:<g>
       where member; scope == own uid — all bands, band-sorted; canEdit true only per §2.4.
       availableGroups via IGroupManager::search('').

POST   /api/v1/rules            create. Body: { type?, userScope?, path, algos?, mode?,
                                enabled?, admin_enforced? }.
       Validation: type ∈ {include, ignore, exclude} (absent → include); include ⇒ algos
       non-empty/valid + mode valid; ignore/exclude ⇒ algos/mode not stored; path glob
       validated as today; non-admin ⇒ userScope forced to caller, admin_enforced forced
       false, isPathWritableByUser required; admin ⇒ any scope (group:<gid> must exist,
       uid must exist); pinned not settable (ignored). Rule appended at end of derived band.

PUT    /api/v1/rules/{id}       update, same validation. Toggling = updating `enabled`
                                (NO separate toggle endpoint — deliberate). Pinned rule:
                                scope/path pinned server-side regardless of payload; enabled,
                                mode, algos, admin_enforced(=stays admin-only) editable.
                                Band change via flag/scope edit ⇒ append at end of new band.

DELETE /api/v1/rules/{id}       404 unknown id; 403 not permitted (§2.4); 400 pinned rule.

PUT    /api/v1/rules/order      Body: { band: 1..6, ownerId?: string, orderedIds: string[] }.
       band 7 is not orderable. orderedIds must be EXACTLY a permutation of that band's IDs
       (band 4: of the segment owned by ownerId — required for admins there; forced to the
       caller for non-admins, whose band must be 4). 400 on any mismatch. Replaces
       RuleService::reorderRules() (the d548d86 design) entirely.
```

Error shape everywhere: `{ success: false, error: "<message>" }` with 400/403/404/500 as per
the existing controller pattern (`InvalidArgumentException` ⇒ 400, capability ⇒ 403, unknown
id ⇒ 404, logged Throwable ⇒ 500).

### 4.2 Status — merge, not move (v1.1 change)

`GET /api/v1/status` (existing, `PublicApiController`) becomes the **only** status endpoint:

```
{ version, dbVersion, rowCount, pending: { total: int, byMode: { "<mode>": int, ... } } }
```

Flat for every authenticated caller — **no capability gating** (verified 2026-08-24: the
public endpoint already exposes version/dbVersion/rowCount/pending-total; the only "admin"
delta was the per-mode split of an already-public total — nothing left worth gating). No
`?fields=` (client-side trimming is not authorization, and a four-field payload doesn't need
selection). `SettingsController::getStatus()` and its route die. Wiring: `getPendingStats()`
lives on `MetadataService`; `StatusService` already injects `MetadataService`, so add
`StatusService::getPendingStats()` delegating to it and let `ChecksumApi::getStatus()` build
the `pending` object from `StatusService` alone (one door).

### 4.3 Settings — actual settings only

Admin-only (no `#[NoAdminRequired]`).

```
GET    /api/v1/settings/permissions/{key}
       → { success, allowAllUsers, groups, users, availableUsers, availableGroups }
PUT    /api/v1/settings/permissions/{key}     Body: { allowAllUsers, groups, users }
```

`{key}` validated against `PermissionService`'s map; unknown key → **404** (it is a resource
path). `rule_editing` is the only key now; `manual_recalc` / `api_access` (Features 6/7) later
land as one map line each. Replaces `/settings/admin-options*`. `PermissionService` itself
needs no change.

## 5. Frontend

- **One table** for all rules (admin page) — the separate global-rule table and its shared-
  colgroup hack die. Server delivers band-sorted; render in that order. Row 7.1 (pinned):
  no drag handle, no Delete, Edit opens the dialog with scope/path locked (existing
  `lockScope` mechanics).
- **Band presentation:** per-band row background tint via CSS custom properties derived from NC
  theme vars (theme-aware, light+dark); a thin separator between band blocks; the band is also
  always visible textually via the `<band>.<order>` Priority cell — **never color-only**
  (accessibility requirement).
- **Drag:** handle only on rows the caller may reorder (§2.4). A drop is valid only within the
  dragged row's own band — and, in band 4 on the admin page, within the same owner's segment.
  On drop, emit `{ band, ownerId, orderedIds }` for that band/segment only. This supersedes
  `d548d86`'s cross-list splice logic. Keyboard reorder stays deferred (recorded §8).
- **Dialog (`RuleForm`):** fields in order — Type (include/ignore/exclude — available to
  personal callers too; a user excluding their own files from defaults is legitimate), Scope
  (admin: Global / Group+picker / User+picker; personal: static text "User rule (you)"),
  Enforced (admin only; hidden on personal), Path, Algorithms + Mode (**hidden when type ≠
  include**), Enabled, plus a live derived-band indicator ("→ evaluates in band 2"). Band is
  never a stored or submitted field. Optional: "Add user rule / Add group rule / Add global
  rule" shortcut buttons that pre-fill Scope (nice-to-have, not required).
- **Personal page:** renders the caller-scoped `GET /api/v1/rules` result as the same single
  banded table — applicable bands 1–3 read-only above, own band 4 editable/draggable, applicable
  5–7 read-only below. Creation fixed to band 4. The "not allowed to edit" banner keys off
  `canCreate`.
- **Composables:** `useAdminSettings` / `usePersonalSettings` converge on the new endpoints
  (much of their rule logic can merge into a shared `useRules` composable — implementer's
  choice, but do not leave two copies of identical fetch logic).

### Block 7 — CLI rule controls  *(new in v1.2; own commit; [TASK]; last)*

Deliberately last: the semantics it exposes must be settled by Blocks 3–6 first, and it is
additive — nothing else depends on it.

`occ file-checksum-search:generate` currently honours rules with no way to deviate, which is
right as a default but leaves an administrator with only "edit the rule, run, restore it" for a
one-off. Three additions, in the order they matter:

1. **`--with-ignored`** — also process files whose governing rule is `ignore`. Defensible on its
   own terms: `ignore` means "not automatically, but when asked", and an administrator typing a
   command *is* asking. Does **not** affect `exclude`.
2. **`--ignore-rule=<rule_id>`** (repeatable) — evaluate as if the named rule did not exist, so
   the next matching rule decides. Narrower and more honest than a blanket `--force`: it names
   what is being set aside, appears in shell history and cron lines, and cannot be mistaken for
   permission to read every excluded mount. **Not** a general override — a file with no other
   matching rule still falls through to the default.
   *Open question for execution:* should `--ignore-rule` be able to set aside an
   `admin_enforced` rule? It is an admin-only command by construction (shell access as the web
   server user), so "yes" is defensible; but an enforced `exclude` on a metered mount is exactly
   the thing whose cost does not care who is asking. **Recommendation: allow it, log it at
   warning level naming the rule.** Confirm before implementing.
3. **`-v` / `-vv`** — per-file reporting of which rule decided and what the verdict was.
   Currently a skipped file is only a count; the reason is invisible. `-v` prints one line per
   skipped file (path, rule id, verdict), `-vv` prints one line per file including the ones that
   proceeded. Symfony Console's `OutputInterface::VERBOSITY_*` already carries this — no new
   options needed, just checks in the marking loop.

Explicitly **rejected**: a blanket `--force`. The rules are a statement of intent about the
storage (`exclude` on a metered mount means reading costs money), not a trust boundary, and its
main practical use would be doing the expensive thing the configuration exists to avoid — most
likely from a cron line nobody is watching. The escape hatch that already exists (edit the rule,
run, restore) leaves the intent visible in the rule list the whole time.

*Files:* `lib/Command/GenerateHashes.php`, `tests/Unit/Command/GenerateHashesTest.php`,
README's CLI reference, `CHANGELOG.md`.
*Tests:* `--with-ignored` processes ignore but still skips exclude; `--ignore-rule` falls through
to the next matching rule rather than blanket-allowing; an unknown rule id is a clear error, not
a silent no-op; `-v`/`-vv` output shape; and that plain invocation is unchanged.

## 8. Reserved (recorded, deliberately not built)

- **`pass` verb** — fall-through verdict (firewall `RETURN`); a third… fourth type, never a
  variant of exclude.
- **`allowManual: false`** on include rules — "system maintains, users may not recompute"
  (drift-protection; Feature 5 territory).
- **`mode: opportunistic`** — hash only when content is in transit anyway; requires storage-
  wrapper/stream machinery (no read hook exists; range requests break whole-file hashing; even
  the write path currently re-reads at processing time).
- **`allowed_modes`** — per-rule/band constraint on which modes may be used.
- **Keyboard reorder** (Ctrl+↑/↓) — frontend-only follow-up; focus-retention after re-render is
  the known care point.
- **`/api/v1/preferences/{key}`** — namespace reserved; first tenant: Feature 5's
  drift-notification opt-out.
