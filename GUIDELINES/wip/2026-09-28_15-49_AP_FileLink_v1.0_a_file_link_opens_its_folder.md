# AP FileLink v1.0: a file link opens its folder

> **Status: proposal, 2026-09-28.** Reported on jackal (Nextcloud 33.0.5,
> app 0.20.2) as user `mdr`: a row on the Duplicates page opened Files with
> the toast "The file could not be found", although the file exists.

## Discussion

**The 605 files with SHA-1 `da39a3ee…`** are empty files, as supposed:
that value is the SHA-1 of no input. On jackal every one of the 1,477 index
rows carrying it has `size = 0` in `oc_filecache`, and every indexed
empty file carries it. Nothing is wrong with the hashing. Whether the
Duplicates page should leave empty files out is a separate decision and not
part of this AP.

## Analysis

1. **Both link builders drop `dir`.** `fileUrl()`
   (`src/duplicates-vue/composables/useDuplicates.ts`) and `fileLink()`
   (`src/sidebar-vue/ChecksumsSidebarTab.vue`) build
   `/apps/files/files/{fileid}?opendetails=true`. The commit "[FIX] Link a
   row only where the link would open" (released in 0.20.0) dropped `?dir=`
   as never read.
2. **Core reads it.** `ViewController::index()` (stable33 and master alike)
   redirects to the file's folder only when `$dir !== ''`. Sent none, it
   renders the root, and `FilesList.vue`'s `mounted()` shows "The file could
   not be found" when the id is not in it. Only files in the viewer's root
   folder open.
3. **Measured on jackal**, file 1260561, basic auth as `mdr`:

   | Request | Answer |
   |---|---|
   | `/index.php/apps/files/files/1260561?opendetails=true` | 200, the root listing |
   | `/index.php/f/1260561?opendetails=true&openfile=false` | 303 to `/apps/files/files/1260561?dir=/arbeiten/Axialis%20Librarian/Media%20Files/Images&openfile=false&opendetails=true` |

4. **`/f/{fileid}`** (`files.view.showFile`) is core's own entry point for
   a link by id: `redirectToFile()` finds the node in the viewer's folder
   (`getFirstNodeById`), sets `dir`, and forwards `opendetails` and
   `openfile`. Same in 33 and 34. `HashSearchProvider` already links there.
   `openfile=false` is needed: for a file, `redirectToFile()` defaults it to
   `true`, which opens the viewer instead of the details pane.
5. **Rejected: restoring `?dir=` from `file.path`.** The path is the
   listing's; the server knows the viewer's folder at click time, including
   received shares and group folders.
6. **`openableBy()` still holds**: `/f/` resolves in the viewer's own folder
   too. Its docblock names the old route.
7. **Why nothing caught it.** The spec asserts the absence of `dir=`; every
   e2e spec visits a file page with a hand-built `dir`, and none follows a
   row's link.

## Implementation Plan

### Block 1 — one link builder

1. `src/routes.ts`: `FRONTEND.fileLink` becomes `/f/{fileid}`, its comment
   saying why.
2. New `src/fileLink.ts`: `fileLink(fileid)` returns
   `generateUrl(FRONTEND.fileLink, …)` plus `?opendetails=true&openfile=false`,
   the docblock carrying the reasoning of Analysis 2 and 4.
3. `useDuplicates.ts` `fileUrl()` and `ChecksumsSidebarTab.vue` `fileLink()`
   call it; their "No `dir`" comments go.
4. `lib/Public/ChecksumApi.php` `openableBy()`: the docblock names
   `/f/{fileid}`.

**Verification:** `npm run lint`, `npm run build`, `composer cs:check`,
`composer psalm`.

### Block 2 — tests

1. New `src/fileLink.spec.ts`: the link is `/f/{id}`, opens the details
   pane, not the file, and carries no `dir`.
2. `useDuplicates.spec.ts`: the `fileUrl` case asserts the same through the
   composable, its comment corrected.
3. `tests/e2e/duplicates.cy.js`: a Mine row's link, requested without
   following redirects, answers 303 to a location with
   `dir=/fcias-e2e-duplicates`, `opendetails=true` and `openfile=false`.

**Verification:** `npm test`; `npx cypress run --spec
tests/e2e/duplicates.cy.js` against harness instance 34.

### Block 3 — changelog, quality pass

1. `CHANGELOG.md`, `## [Unreleased]` → `### Fixed`:

   ```text
   - Opening a file from the Duplicates page or the sidebar's duplicate
     list: "The file could not be found" for a file outside the root folder.
   ```

2. Quality pass (`GUIDELINES/shared/QUALITY.md`) over every changed file;
   `npm run lint:fix` for `.ts`/`.vue`.

**Verification:** `GUIDELINES/shared/tools/changelog.sh check`.

Not in scope: deploying to jackal. The fix reaches it with the next release.

## Proposed commit message

```text
[FIX] A file link opens the file's folder

A file link on the Duplicates page and in the sidebar's duplicate list opened Files on the root folder, which says "The file could not be found" for any file not in it.

Key changes:
- one link builder for both, to core's `/f/{fileid}`: it finds the file's folder in the viewer's files and redirects there, details pane open and file not opened
- `openableBy()`: its docblock names that route
- tests: the builder's spec, and an e2e case that follows a Duplicates row's link to its folder

Core's `/apps/files/files/{fileid}` works out the folder only when a `dir` is sent; sent none, it lists the root. "[FIX] Link a row only where the link would open" had dropped `dir` as never read.

AP FileLink v1.0.
```
