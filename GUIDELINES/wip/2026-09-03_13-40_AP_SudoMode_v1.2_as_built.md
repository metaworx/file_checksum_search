# AP SudoMode v1.2: as built

> **Status: closing record, 2026-09-03.** Supersedes v1.1 (d88e27e) with
> what was actually built, where it differs. Nothing here is a plan: every
> block is committed, and this exists because v1.1 is immutable and would
> otherwise be the last statement of intent on three points that changed
> during execution.

## What changed against v1.1

1. **Route naming.** `/api/v1/sudo/…`, a prefix mirroring the ordinary
   routes one for one, ruled by the user; replaces `/any` and `/all`.
2. **Confirmation mechanism.** Core's `#[PasswordConfirmationRequired]` is
   not on the sudo routes. Its middleware refuses an app-password session
   outright — such a session has no confirmation, and strict mode checks the
   account password — so a granted token could never pass it. The check is
   the app's own, `SudoConfirmation`: `last-password-confirm` within thirty
   minutes (core's own window, read from core's own session key) or a
   granted app password. Core's dialog still sets that key, so block 4's
   page flow is unchanged. Two core-private session keys are read
   (`app_password`, `last-password-confirm`); the coupling is named in the
   class and is of the same kind as the `oc_authtoken` read.
3. **A dangling grant is unreachable, not refused.** A deleted token cannot
   authenticate at all, and `oc_authtoken.id` is never reused; the only
   handling is cosmetic — dropped from the owner's list, shown as such on the
   admin tab.
4. **Two permissions ship allowed.** `api_access` and `manual_recalc` default
   to allow-all, and an administrator is never locked out of either: every
   script and every sidebar that worked before the upgrade works after it,
   until an administrator narrows. `instance_view` and rule editing remain
   grants. The HTTP integration suite found the first of these by failing
   on the original default.
5. **Order.** 1, 2, 3, 4, 7, 5, 6 — the API permission before the token page
   it hides.
6. **Token scope.** A token kept out of the filesystem is refused on every
   route (`ILockdownManager::canAccessFilesystem()`, block 1) and cannot be
   granted (block 5).

## Deferred

- The sub-admin user picker (ruling 4): the authorisation rule is built and
  tested; the control that would let a leader name a member is not.
- An integration test that exercises a sudo route with a granted app
  password end to end. The rule is unit-tested in `SudoConfirmation`; the
  wiring is not exercised over HTTP.
