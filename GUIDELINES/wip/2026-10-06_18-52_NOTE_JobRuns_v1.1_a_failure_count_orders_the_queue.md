# NOTE JobRuns v1.1: a failure count orders the queue

Decided with the user, 2026-10-06, after v1.1 was presented. It replaces
Block 1, step 2's cursor; steps 1 and 3 stand.

- **A failure count in the state row.** When `processFile()` throws, the
  drain, the job's and the CLI's alike, adds one to the file's state row's
  `meta_value_int` (`meta_value_int + 1`, which every supported database
  takes). The row is this app's alone, which Nextcloud never rewrites; its
  int column is written 0 today and read by nothing.
- **No `:error` in the marker.** It would say what a count above 0 says,
  and change the marker for its readers: `parseMode()` would hand
  `processFile()` a mode of `auto:error`, `getPendingStats()` would group
  every mode twice, and each comparison with a mode would need a second
  spelling.
- **A re-mark keeps the count.** A file queued again while it is queued
  keeps its place, so a sweep cannot reset the order on every tick. A
  successful hash deletes the row, and the count with it. The count orders
  the queue; it never takes a file off it.
- **The fetch orders by count, then file id.** Where that costs too much on
  a large queue, measured on the harness, it becomes two fetches: the files
  never tried first, then the rest.
- **The runs stop on their own.** `queue:drain --all` ends when a batch
  hashed nothing: only failing files are left by then. The job re-dispatches
  only after a full batch that hashed something.
- **No terminal state.** A failure is mostly passing, an external storage
  offline or a lock, and a parked file would stay unhashed until it
  changed. A failing file is retried behind every other.
- **The log warns once.** A file's first failure is a warning, those after
  it debug, where every attempt warns today.
- **Block 2's status** shows how many queued files have failed at least once.
