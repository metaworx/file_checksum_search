# NOTE JobRuns v1.1: a failed attempt raises the count

Decided with the user, 2026-10-06, after Block 1's first step. It corrects
*NOTE JobRuns v1.1: a failure count orders the queue* where that note
counts only an exception.

- **What step 1 found.** A file the drain cannot read does not throw:
  `recalcHashes()` catches every read error, and reports a lock or a write
  during the read as busy; `applyBatchResults()` then queues the file again
  and `processFile()` returns as though it had hashed it. Both drains
  counted it hashed and took it again: `queue:drain --all` without end, and
  the job behind a batch of such files for ever. An exception comes only
  from the metadata or database layer.
- **A failed attempt raises the count by one.** Wherever an attempt leaves
  the file queued: `applyBatchResults()`, in place of its `markPending()`,
  which rewrote the row and so set the count back to 0; and the drains,
  where `processFile()` throws. A file the attempt finds not queued is
  queued with it, as `markPending()` did.
- **Every other mark keeps the count.** A write, the rule sweep, a rule
  applied, the clearing of a disowned file: the sweep queues every file
  whose hashes are older than it, which a file that keeps failing stays.
  A mark may change the mode; only the int column is kept. The count goes
  when the file leaves the queue: hashed, dropped, or eroded.
- **`processFile()` says whether the file left the queue.** Both drains
  count hashed and failed files by it, and "a batch that hashed nothing" is
  a batch in which no file left the queue.
- **One fetch, ordered by count, then file id.** Measured on harness
  instance 34 (MariaDB) with 200,000 `stale:reset` rows and 2,000 queued:
  with table statistics, both orders read the queued rows through
  `fcias_f_metadata_str_idx` and sort them; the count's order takes 5 ms a
  fetch against 1.5 to 1.8 ms, the count being read from the row. Two
  fetches would not read fewer rows.
