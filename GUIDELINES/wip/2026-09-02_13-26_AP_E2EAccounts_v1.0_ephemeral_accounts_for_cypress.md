# AP E2EAccounts v1.0: ephemeral accounts for Cypress

> **Status: preliminary — not yet approved.** Was queued behind AP\_E2ETests
> v1.1, which is finished and retired.

## Discussion

The PHPUnit integration suite was moved off fixed accounts on 2026-09-01
(`263d627`): `DatabaseTestCase::makeAccount()` creates a randomly named account
with a random password for the run and deletes it afterwards. The Cypress suite
was left on the old pattern deliberately, to be done after v1.1 rather than
during it.

It still authenticates as `alice` and `bob` with `SecretPass123!`, and
`cy.fciasEnsureUsers()` creates them under exactly those names when missing —
and never deletes them, because on the developer instance they are the
developer's own accounts, not the suite's.

A predictable account with a password published in the repository is standing
risk on every instance the suite has ever touched. The random name is also what
removes the "may I delete this?" question: the suite only ever deletes what it
made.

**Smaller than when this was queued.** The memory recording it names
`rules-api.cy.js`, which v1.1 retired. Four occurrences of the password remain,
and exactly one spec is affected.

| File | What is in it |
|---|---|
| `tests/e2e/rules-personal.cy.js:26-27` | the `alice` / `bob` constants |
| `tests/e2e/support/e2e.js:248-262` | `fciasEnsureUsers`, which hardcodes both names and the password |
| `tests/e2e/README.md:115` | the helper's row, which prints the password |

## Analysis

### The spec already owns its fixtures

An earlier reading of this expected the accounts to be entangled with the
developer instance's own data. They are not: the spec `MKCOL`s its own
`fcias-e2e-shared` and `fcias-e2e-private` folders, writes its own files, and
creates the share between the two accounts itself through OCS. Nothing it
asserts depends on `alice` and `bob` pre-existing, or on being called that.

`cy.fciasEnsureUsers` is called from one place — `rules-personal.cy.js:100` —
so the helper is replaced outright rather than kept alongside a new one.

### Session caching is unaffected

`cy.login()` keys `cy.session()` on `[user, password]`, so a per-run pair simply
produces a per-run cache key. No spec sets `cacheAcrossSpecs`, and no other spec
logs in as either account, so nothing reuses a session across the boundary where
the names change.

### Teardown, and what a failed one leaves

Deletion goes in the existing `after()`, after `fciasResetRules` — the admin's
enforced rule names `home:<alice>`, and clearing rules before the account keeps
the ordering truthful rather than merely working.

A crashed run still leaves an account behind. That is acceptable and is the
point of the change: what it leaves has a random password and a
`fcias_e2e_`-prefixed name, so it is inert and identifiable, where `alice` with
a published password is neither.

### Passwords

Composed the way `makeAccount()` composes them — upper, lower, digit, symbol,
then random fill to 32 — so the result satisfies any password policy the
instance has switched on rather than passing by luck. Generated with
`crypto.getRandomValues()`, which the spec has because Cypress specs run in the
browser.

## Implementation Plan

### Block 1 — ephemeral accounts · `[TASK]`

1. `support/e2e.js`: replace `fciasEnsureUsers` with
   `cy.fciasMakeAccount( occ, base )`, yielding `{ user, password }` for a
   freshly created `fcias_e2e_<base>_<hex>`, and `cy.fciasDeleteAccount( occ, user )`.
2. `rules-personal.cy.js`: `alice` and `bob` become `let`, assigned in
   `before()`; `after()` deletes both after the rules reset.
3. `README.md`: the helper table row, and the two prose mentions of the pair.
4. `npm run lint`.

**Verification:** full e2e suite green twice. `grep -rn SecretPass123 tests/`
empty. After a run, `occ user:list` shows no `fcias_e2e_*` account — and the
developer instance's own `alice` and `bob` are still there, untouched, which is
the assertion that the suite stopped adopting accounts it did not create.

## Open decisions

1. **Keep the names readable?** `fcias_e2e_alice_9f3a1c04` keeps a failing run's
   output legible about which account is which, at the cost of saying that two
   of them are a sharer and a sharee. A bare `fcias_e2e_9f3a1c04` says nothing
   to an attacker and nothing to a reader either. The plan above assumes the
   readable form.
