## Decisions taken (from v1.2)

1. **Search result name:** *File Checksums* — short. The provider stays; the
   guide's sentence changes.
2. **Sidebar quick buttons:** not fixed. First = the user's preferred algorithm,
   set on their personal settings page. Second = the first algorithm of the
   file's governing rule that is not the preference. One button when they
   coincide.

## Discussion

### The algorithm list is compiled in, in two languages

`HashCalculationService::SUPPORTED_ALGOS` names eight; `src/algorithms.ts`
mirrors it by hand, with a canary test on each side that fails when they drift
(`HashCalculationServiceTest::testSupportedAlgosMatchesFrontendMirror`,
`algorithms.spec.ts` "matches the PHP backend mirror exactly"). The Duplicates
page then hard-codes **seven** of them anyway. PHP here offers 60 — including
`sha384`, `sha3-384`, `sha512/256`, `xxh3`, `blake`-less but `ripemd160`.

Two constraints shape a catalogue:

- **Names become metadata keys** (`file-checksum-hash-<algo>`) and are parsed
  back by prefix strip (`getAlgorithmenFromKey()`). `/` and `,` in
  `sha512/256` or `tiger192,3` would be legal to PHP and hostile to a key.
  Catalogue names are restricted to `[a-z0-9-]+`.
- **Length is already handled.** `isTruncatable()` is length-based, so a
  96-hex `sha384` takes the same truncate-and-confirm path `sha512` does. No
  new code for long digests.

### Where each new thing lives

| Thing | Backend | API | Frontend |
|---|---|---|---|
| Catalogue | `AlgorithmCatalogue` service: `hash_algos()` ∩ admin allowlist, name-filtered. Replaces the constant and the two static helpers (`isValidAlgo`, `getDefaultAlgo`; callers: `RuleDefinitionValidator` ×2, `ChecksumApi` ×1, four `MetadataService` key-registration loops). | `GET /api/v1/algorithms` → `{algorithms, default}`; the rules payload's existing `supportedAlgos` reads from it | `SUPPORTED_ALGOS` and both canaries retire; Duplicates page and sidebar fetch the list |
| Admin allowlist | lexicon `allowed_algorithms` (STRING, JSON list; default the eight + `sha384` + `sha3-384`) | `admin-options` gains `allowedAlgorithms`, saved like `groups`/`users` | `PermissionSection`'s sibling: an `NcSelect` multiple over what PHP offers |
| User preference | lexicon `getUserConfigs()` — currently `[]` — gains `preferred_algorithm` (STRING); read/written via `IUserConfig` | `GET/POST /settings/personal-options` on `SettingsController` (already `#[NoAdminRequired]`) | personal page: an `NcSelect` above the rules table |
| Governing rule's algos, for the sidebar | `getHashesByFileId()` learns the governing rule (`RuleService::findFirstMatchingRule`) | `/file/{fileId}/hashes` response gains `algos` (the rule's, or `[]`) and `preferred` | sidebar composes the buttons from `preferred`, `algos`, `default` |

### Duplicates page controls

`NcSelect`, `NcCheckboxRadioSwitch`, `NcTextField` (`type="number"`) and
`NcButton` all exist in the installed `@nextcloud/vue` 9 and three are already
used elsewhere in the app, so the page joins the house style rather than
introducing one. The algorithm select gets its label by construction; `adler32`
arrives by construction, because the options are the catalogue.
`duplicates.cy.js` drives the checkbox as `.db-label input[type="checkbox"]`;
`NcCheckboxRadioSwitch` hides its input, so the spec moves to the component's
label or `check({ force: true })`.

### Sidebar button composition

```
preferred  := user's preferred_algorithm, if set and in the catalogue
ruleAlgos  := governing rule's algos (may be [])
first      := preferred ?? ruleAlgos[0] ?? default
second     := first of ruleAlgos not equal to first  (none → no second button)
```

A file no rule governs and a user with no preference gets one button, the
catalogue default. The picker for everything else stays.

## Implementation Plan

### Block 1 — the catalogue · `[TASK]`

1. `AlgorithmCatalogue` with the name filter; the constant and statics go;
   the seven callers move. Unit tests: filter rejects `sha512/256`, allowlist
   honoured, unknown allowlist entries ignored, default present.
2. Lexicon `allowed_algorithms`; `admin-options` GET/POST carry it; admin UI.
3. `GET /api/v1/algorithms`; rules payload reads from the catalogue.
4. Retire `SUPPORTED_ALGOS` and both canaries — the cross-language mirror they
   guarded no longer exists.
5. Docs: `api-v1.md` and the OpenAPI enums at three sites become "any name the
   instance's catalogue lists" with the default set named; README/FAQ lists
   become defaults-plus-admin-extension.

### Block 2 — the Duplicates page · `[TASK]`

6. The five controls to Nc components, options from the catalogue.
7. `duplicates.cy.js` selectors follow. Full e2e.

### Block 3 — preference and sidebar · `[TASK]`

8. Lexicon user config; `personal-options` endpoint; the personal page control.
9. `/file/{fileId}/hashes` gains `algos` + `preferred`; documented in
   `api-v1.md` and OpenAPI (`FileHashesResponse`).
10. Sidebar composes its buttons; **Recalc** → **Recalculate**. Unit tests on
    the composition table above. Full e2e — `checksums.cy.js` clicks the
    `[data-algo="sha1"]` button, which exists only if the composition yields it;
    the spec seeds a preference or asserts on the composed set instead.

### Block 4 — the sentences · `[TASK]`

11. Every row of v1.2 §B, plus: the preference control, the composed buttons,
    the admin allowlist, "File Checksums" as the search result's name.

Each block carries its CHANGELOG bullet; Blocks 1–3 are shipped behaviour.

## Open decisions

1. **Default allowlist.** The eight plus `sha384` and `sha3-384` is assumed.
   Anything else PHP offers is one admin click away.
2. **Preference default when unset.** Assumed absent — the first button is then
   the rule's first algorithm, not a global default — so a user who never
   visits settings sees what their rules compute. Alternative: default to the
   catalogue default for everyone.
