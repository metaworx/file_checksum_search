# AP JobRuns v1.1: run outcome and execution mode

## Discussion

- **Origin.** Carried over from AP SuggestedFeatures v1.5 (2026-08-22), at
  the user's request of 2026-09-30: its run-history and execution-mode
  feature, less what is built.
- **Re-evaluated 2026-10-06**, at the user's request, against Nextcloud 33
  and 34 as they are now. This revision follows from it.
- **The execution mode is dropped.** Nextcloud's own worker covers running
  the jobs outside `cron.php` (Analysis), which leaves documentation. A mode
  that keeps `cron.php` from running the app's jobs is not planned: there is
  no API for it, and `run()` would have to guess who called it. It comes
  back only if the user asks for it.
- **Not scheduled.** It is re-confirmed with the user before it runs.

## Analysis

**Built:** each background job records when it last ran and a few counts
(`JobStatsService`), and `occ file-checksum-search:status` and the admin
status panel show them.

**What Nextcloud records of a run:**
- **34:** every run, from `cron.php` (`CronService`) and from
  `occ background-job:worker`, with its duration in ms, its peak memory
  and a status, readable through `OCP\BackgroundJob\IJobRuns` (since 34)
  and listed by `occ background-job:history`. A failure never shows:
  `Job::start()` catches every exception (core's own TODO), so a run ends
  `SUCCEEDED`, or `CRASHED` when the process died.
- **33:** the last run's duration in whole seconds, in `oc_jobs`, shown by
  `occ background-job:info <id>` and not readable through OCP.

**The gap is the outcome, and it is worse than missing:** every job catches
its own exception, logs it, and skips `JobStatsService::record()`. The
status keeps the last *successful* run, so a job that fails on every tick
reads as one that ran a while ago. Rethrowing would not help: core records
the run as succeeded either way. `ApplyRuleJob` records nothing at all.

**Running the jobs outside `cron.php`** needs no app code:
- `occ background-job:worker <job-classes>` (33 and 34) runs only the
  classes it is given, in its own process, so under `nice`/`ionice`, with
  `--once` and `--stop_after`;
- `occ fcias:queue:drain [--all]` drains the queue from an
  administrator's own crontab.

The three questions of v1.0 answer themselves: the worker takes job
classes, so the choice is per job; the jobs stay registered, since the
worker reads them from `oc_jobs`; and `cron.php` and the worker share the
job's reservation, so one job never runs twice at once. What can overlap is
the CLI drain or `fcias:hash` beside the job: `fetchPendingBatch()` claims
nothing, so both may read the same file. Double reads, no harm known; not
planned.

**A loop to confirm:** `fcias:queue:drain --all` stops only on an empty
fetch. A file whose `processFile()` throws stays marked (`Drain`'s own
comment), and `fetchPendingBatch()`, ordered by file id, returns it again,
so a file that always fails would keep `--all` running forever. The
background drain has the same root: a batch full of such files is retaken
on every tick and re-dispatched, and the files behind it are never reached.
Whether any path through `processFile()` throws and leaves the mark is
what the first test establishes.

**Constraints:**
- every new text is translatable, in every language kept here;
- `npm run typecheck` stays at zero errors;
- the checksum count's record (`counts.rows` of `checksum_count`) and the
  existing `stats_<job>_last_run` keep their meaning.

## Implementation Plan

### Block 1: a file that keeps failing does not stall the drain

1. A test that a file `processFile()` cannot hash, on every attempt, ends
   `queue:drain --all` with that file counted failed and still marked; a
   unit test for `Drain`, with a guard that fails it rather than hanging,
   and one for `ProcessPendingUpdates` with a batch of such files.
2. Where a path through `processFile()` throws with the mark left
   (integration), the fix: the drain walks the queue by file id from a
   cursor, `fetchPendingBatch()` taking an optional lower bound. The CLI
   keeps the cursor for its run, so one run passes every file once; the
   job keeps it in app config and starts again from the lowest id when a
   fetch comes back short. A failing file is retried once per pass.
3. Where no path does, the test stays, and the block ends there.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS, Psalm.
**CHANGELOG:** Fixed, if a fix is made: `queue:drain --all` and the
background drain past a file that keeps failing.

### Block 2: a run's duration and outcome

1. `JobStatsService`: a run's duration in ms, its outcome (`ok` or
   `failed`) and, when it failed, a short reason (the exception's class and
   message, truncated), recorded beside the last run; the last successful
   run kept apart from the last attempt. A failure is recorded by the job
   that met it, through a method of its own that never throws.
2. Every job times its run and records a failure in its `catch`, the orphan
   purge and the checksum count included; `ApplyRuleJob` gets a record of
   its own.
3. `occ …:status` and the admin status panel: the duration, and a failed
   last attempt with its reason and the time of the last success.
4. Tests: unit for recording and reading back an ok and a failed run, a
   job that ends normally and one that throws, and the status output;
   Vitest for the panel's rows.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS, Psalm,
Vitest, `npm run typecheck`, ESLint, stylelint and `scripts/l10n.sh check`.
**CHANGELOG:** Added: each job's last run with its duration and outcome.

### Block 3: running the jobs outside `cron.php`

1. `docs/FAQ.md`, beside *How does cron / pending processing work?*: the
   app's jobs under `occ background-job:worker`, with `nice`/`ionice`;
   `fcias:queue:drain` from a crontab; and, on Nextcloud 34,
   `occ background-job:history` for their past runs. `README.md`'s
   *Pending Hash Queue* points there.

**Verification:** the commands run on harness instances 33 and 34 as
written.
**CHANGELOG:** none: `docs/` and `README.md` only.
