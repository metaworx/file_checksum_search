# NOTE JobRuns v1.1: queue:drain --all walks the queue once

Decided with the user, 2026-10-07, at Block 1's commit gate. It corrects
*NOTE JobRuns v1.1: a failure count orders the queue*, whose "`--all` ends
when a batch hashed nothing" the user meant as "nothing is left that this
run has not tried". Read as written, a batch of untried files that all
failed, an offline storage at the head of the queue, ended the run with
untried files behind it.

- **`--all` tries every queued file once.** It walks the queue by file id
  from a lower bound, `fetchPendingBatch()` taking it, past each file
  whether it hashed or not, and ends on an empty fetch. A file that fails
  is passed, not taken again; one queued behind the walk waits for the next
  run. Without `--all`, one batch in the queue's own order, as before.
- **Not the count's order, skipping the files tried.** A file with more
  failed attempts from earlier runs sorts behind one that failed once in
  this run, so a fetch of tried files alone does not show that nothing
  untried is left; and excluding the tried ids in SQL grows with every
  failure, against the bound-parameter limits of SQLite (32,766) and
  PostgreSQL (65,535).
- **The job keeps its rule**: no re-dispatch after a full batch in which no
  file left the queue. It has no memory between runs, and a re-dispatch
  would let `cron.php` take the same failing files again within one cron
  run. At the next tick the untried files come first, the failed ones
  sorting behind them; a batch that failed whole delays the rest by one
  interval, 60 seconds by default.
- **No threshold of failed files per storage.** Nextcloud wraps every
  external, non-local storage in `OC\Files\Storage\Wrapper\Availability`:
  after its first `StorageNotAvailableException`, every call fails at once
  for 10 minutes, 30 for an authentication failure, so an offline storage
  costs one backend timeout and then milliseconds a file. Many failures in
  one storage mostly mean a folder, permissions or a sync's locks, and
  skipping the storage would leave its healthy files unhashed.
- **Block 2 asks `IStorage::getAvailability()`** before the lock and the
  metadata load, counting the attempt at a file on a storage Nextcloud
  knows is down without that work, with "storage unavailable" as its
  reason.
