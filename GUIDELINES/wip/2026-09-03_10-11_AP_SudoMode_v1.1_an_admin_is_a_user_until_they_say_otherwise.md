# AP SudoMode v1.1: an admin is a user until they say otherwise

> **Status: approved 2026-09-03, in execution.** Supersedes v1.0 (ab38cf8),
> whose two open decisions are ruled and whose scope grew by the four
> questions that followed. Everything below was checked against Nextcloud
> 34.0.3 on instance 34 before being written down.

## Rulings

1. **The break is accepted.** Administrators are scoped to their own files
   by default, on every read path. Stated under `### Security` with a
   migration note for anyone scripting against the API with admin
   credentials.
2. **It applies to the sidebar and the unified-search provider too**, not
   only the four public endpoints.
3. **Who may switch: a permission of our own, not a group of core's.**
   `admin` membership is core's whole definition of administrator and cannot
   be widened, so "sudoers" is a third entry in `PermissionService` —
   `instance_view`, allow-all / groups / users, `admin` always — with an
   admin section in the shape the rule-editing one already has.
4. **Team leaders: the rule now, the picker later.** Core's `ISubAdmin` is
   public API and `isUserAccessible($leader, $member)` is exactly "may this
   leader look at this member". The authorisation rule is written now; the
   user picker that would let a leader choose a member is deferred, since the
   current cross-user queries are "one user" or "everyone" and a leader needs
   neither yet.
5. **Tokens: read the table, grant by id.** Core exposes no listing — not in
   OCP, not over HTTP; the Security page's list is server-rendered initial
   state — and without a listing a name-based grant is first-caller-wins,
   which is not a guarantee. This app already reads five core tables through
   the query builder, so one more `SELECT id, uid, name, type, last_activity
   FROM oc_authtoken`, behind one repository class, adds no new class of
   dependency. Only app passwords (type 1) are grantable; browser sessions
   (type 0) are made and discarded by logging in.
6. **Grants live in user config.** One lexicon `ARRAY` key per user,
   `sudo_tokens` → `{ tokenId: { granted_by, granted_at } }`, beside
   `preferred_algorithm`. `IUserConfig::getValuesByUsers()` enumerates it
   for the admin tab in one call; core's `User::delete()` removes it with
   the account. A grant whose token no longer exists is dropped as it is
   listed and refused at request time.
7. **Features 6 and 7 of SuggestedFeatures fold in** as two more permission
   keys — `manual_recalc`, `api_access` — three keys, three sections of the
   same shape, separate commits under this AP. The generic `PermissionService`
   that feature 6 asked for already exists; the session-versus-token spike
   feature 7 asked for is answered by the same token lookup as ruling 5.

## How the pieces fit

Every cross-account read answers one question, in this order:

1. Is the caller a **sudoer** — `admin`, or in `instance_view`? Then they
   may look at anyone, once confirmed.
2. Otherwise, is the caller a **sub-admin** of a group the target is in?
   Then they may look at that member, once confirmed.
3. Otherwise: their own files. No prompt, no question.

"Confirmed" means one of two things. Interactively, core's
`#[PasswordConfirmationRequired]` on the cross-account routes: the session
holds a confirmation for 30 minutes, which is the sudo window. Non-
interactively, a request authenticated by an app password whose id carries a
grant — resolved through `IProvider::getToken(sessionId)`, public API. A
token grant is a standing authorisation with no password moment, so it is
listed where an administrator sees every one of them.

The cross-account view is separate routes, because the attribute is per
method and putting it on the ordinary route would prompt on every read.
The ordinary routes pass the caller's own uid; only the new ones ever pass
`null` down.

## Blocks, each its own commit

1. `[TASK]` **Scope everyone.** `resolveRequestingUserScope()` answers the
   caller's uid for all; the sidebar's hashes and the search provider follow.
   The migration note under Security. Tests: an administrator reading a
   foreign file gets 404 like anyone else.
2. `[TASK]` **The `instance_view` permission** and its admin section, the
   `admin` group always included. Tests on the permission; the section's
   spec mirrors the rule-editing one.
3. `[TASK]` **Confirmed cross-account routes.** `/api/v1/duplicates/all`,
   `/api/v1/file/{id}/hashes/any`, `/api/v1/file/{id}/duplicates/any`,
   `/api/v1/lookup/any`, each `#[PasswordConfirmationRequired]`, each
   refusing a non-sudoer with 403 before the attribute is even reached; the
   Duplicates page's `?user=` moves behind the same check, with the
   sub-admin rule deciding the target. OpenAPI and `api-v1.md`. Tests for
   sudoer-confirmed, sudoer-unconfirmed, sub-admin-in-scope, sub-admin-out-
   of-scope, plain user.
4. `[TASK]` **Show all users.** The switch on the Duplicates page, shown to
   sudoers, running core's password confirmation and then reading the `/all`
   route; off returns to own files; not persisted. e2e for both states.
5. `[TASK]` **Token grants.** The `oc_authtoken` repository (read-only, five
   columns, degrades to "listing unavailable"); the `sudo_tokens` lexicon
   key; the request-time check; a *Sudo tokens* list on the personal page
   with a checkbox per app password; a *Sudo tokens* tab on the admin page
   listing every grant against the live table, with revoke. Tests on the
   repository, the check, and both pages.
6. `[TASK]` **`manual_recalc`** — feature 6 as written: the permission, its
   section, enforcement in `recalcHash()` beside the ownership check,
   `canRecalc` in the hashes response, the sidebar button hidden when false.
7. `[TASK]` **`api_access`** — feature 7 as written, with the spike replaced
   by ruling 5: a request whose token is an app password is "the API";
   a browser session is "the app". Enforced across `PublicApiController`;
   the bundled pages keep working for a user denied the API.
8. Docs pass over README, FAQ, user guide, `api-v1.md`, OpenAPI; the
   SuggestedFeatures AP notes features 6 and 7 as delivered here.

Verification per block as usual; blocks 3 and 4 are gated by the full e2e
suite, since they change what an administrator sees.

## Open decisions

- Route naming: `/any` for the per-file cross-account variants and `/all`
  for the instance-wide list. Say if you want one word for both.
- The sudo window: core's 30 minutes. Not configurable in this AP.
