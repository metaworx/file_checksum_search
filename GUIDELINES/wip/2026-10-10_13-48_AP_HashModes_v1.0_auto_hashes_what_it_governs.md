# AP HashModes v1.0: auto hashes what it governs

## Discussion

- **Origin.** Testing MIME types on harness instance 34 on 2026-10-10:
  the default `home:*//**` rule (`auto`) was enabled and reapplied, and
  nothing was hashed, while the drain reported "Hashed 78 files". On
  helioscloud, 11,570 of 12,934 queued files lie in folders gone from disk,
  retried for ever with "could not be hashed" and no reason. The user:
  "the current `auto` mode seems more like manual".
- **Decisions to confirm:**
  - **D1, the modes.** `auto`: the rule's algorithms whenever the file is
    read — its first hashes, and after a change; it never reads a file only
    to add an algorithm. `missing`: the same, and the sweep and Reapply
    also read a current file that lacks one of the rule's algorithms.
    Rejected: shipping the defaults as `missing` and leaving `auto` as it
    is, a trap for whoever picks it.
  - **D2, writes.** Creating or writing a file without hashes queues it,
    under `auto` and `missing`, as a file with hashes is queued now. Today
    it waits for the sweep's trickle (100 files per rule every 5 minutes),
    or for Nextcloud's background metadata event, which fires only where
    another app asks for one.
  - **D3, gone files.** A file the storage says does not exist, on two
    failed attempts in a row, leaves the queue as `stale:gone`: its hashes
    out of search, a stamp so the sweep leaves it, the Untrusted total
    naming it. Two attempts, because one negative answer from a remote
    storage can be a passing fault.
  - **D4, Block 2 is separable.** `missing` reaching an added algorithm
    costs a subquery per rule algorithm in the sweep's page query.

## Analysis

**`auto` today:**
- **Create** (`FileListener::onCreate()`): nothing for a file without
  hashes. `missing` has no case there at all.
- **Write** (`MetadataService::markOutdated()`): queues only a file that
  holds hashes.
- **Drain** (`HashCalculationService::algosFor()`): `auto` computes the
  rule's algorithms the document already has. None: only the stamp is
  written.
- **Sweep and Reapply** (`FilecacheService::pageStorageFiles()` with
  `staleOnly`, `RuleService::applyRule()`): queue `pending:<rule mode>` for
  a file without a stamp or with one older than its mtime. Under `auto` the
  drain then stamps it, and it is fresh for ever.
- **`MetadataListener`** queues `pending:missing` on
  `MetadataBackgroundEvent`. Nextcloud dispatches it only when a
  `MetadataLiveEvent` listener asks for background processing
  (`FilesMetadataManager::refreshMetadata()`); this app does not, Photos
  does for images.
- **Net:** under `auto`, a file gets its first hashes only from a sidebar
  Recalculate, `fcias:hash`, or another app's metadata request. Instance
  34: 200 files governed, one hashed.

**`missing` today:** first hashes through the sweep's trickle; an
algorithm added to the rule reaches a current file only at its next
change, or by `force`.

**Stamps without hashes:** written by `auto` on a file without hashes. The
sweep and Reapply then count the file fresh, under `missing` and
`-m missing` as well. Only `fcias:hash`, which checks each algorithm, and
`force` get past them.

**The drain's report:** `processFile()` returns whether the file left the
queue. A dropped mark, a stamp with nothing computed and a MIME type read
all count as hashed. A failure's reason is in the log only: a warning on
the first attempt, debug after. `ProcessPendingUpdates` records
`processed`, `failed`, `total` and `disowned`.

**Gone files:** a file the filecache lists and its storage does not have
fails as "Unable to open file for reading.", is counted, and is retried
behind the rest for ever. Nextcloud 34 does not remove such rows once
their folder's row is gone: `files:scan` cannot reach them, and
`files:cleanup` removes only the rows of deleted storages.

**Fresh, redefined:** a file is fresh to the sweep and Reapply where its
stamp is at least its mtime and it holds a hash or a state row (queued,
eroded, reset, gone); with Block 2, under `missing`, also every algorithm
of the rule. In the page query these are anti-joins on the index by
`file_id`, which its `file_id`-first index serves. The query is timed on
instance 34, and on helioscloud if the user allows it, before Block 1
commits.

**Constraints:** SQL through `IQueryBuilder` only; every new or changed
text translatable, in every language kept here.

## Implementation Plan

### Block 1: `auto` gives a file its first hashes

1. Drain: under `auto`, a file without a current hash, none or outdated,
   gets the rule's algorithms; the hashes of algorithms the rule does not
   name go, as now. A current file with hashes is unchanged.
2. Create and write, under `auto` and `missing`: a file without hashes is
   queued `pending:<mode>`.
3. Sweep and Reapply: fresh as redefined above, so a file stamped without
   hashes is queued again by the next sweep; no repair step.
4. The mode's help in `RuleTable.vue` and `RuleForm.vue`, in the 11 `.po`
   files; README *Modes* and *How hashing happens*, FAQ *How do rules
   work?*.
5. Tests:
   - unit: the drain's `auto` on a file with none, outdated and current
     hashes; the listeners on a file without hashes;
   - integration: an `auto` rule enabled after the fact hashes an existing
     file through the sweep and through Reapply; a file stamped without
     hashes is queued again.

**Verification:** PHPUnit unit and integration on NC 33 and 34, Vitest,
ESLint, `vue-tsc`, ECS, Psalm, `scripts/l10n.sh check`, the rules Cypress
specs on NC 34; the sweep's page query timed before and after.
**CHANGELOG:** Fixed: rules in `auto` mode hash the files they govern that
have no checksums yet, and files an `auto` pass stamped without checksums
are found again.

### Block 2: `missing` adds an algorithm added to the rule

1. Sweep and Reapply under `missing`: a current file lacking one of the
   rule's algorithms is stale. The drain already computes the absent ones.
2. The mode's help and the README, if Block 1's words do not cover it.
3. Tests: integration: an algorithm added to a `missing` rule reaches a
   current file through the sweep and through Reapply, and not under
   `auto`.

**Verification:** as Block 1, the page query timed with one to three
algorithms.
**CHANGELOG:** Changed: rules in `missing` mode add an algorithm added to
the rule to the files they hashed before.

### Block 3: the drain says what it did with each file

1. `processFile()` returns an outcome: hashed; MIME type read; stamped,
   nothing to compute; dropped, with why (no include rule, detection off,
   a document not current); gone (Block 4); failed, with why (storage
   unavailable, locked, changed while read, read error).
2. `fcias:queue:drain`: the summary counts each outcome; `-v` prints a
   line per file not hashed, with its reason.
3. `ProcessPendingUpdates` records the counts; `fcias:status` and the
   admin status show them; the status text in the 11 `.po` files.
4. Tests: unit for each outcome, the command's output and the job's
   record; Vitest for the status text.

**Verification:** as Block 1.
**CHANGELOG:** Changed: the queue drain, in occ and in the status, counts
files hashed, dropped and failed apart, and `-v` says why a file was not
hashed.

### Block 4: a file gone from its storage leaves the queue

1. A failed read asks the storage whether the file exists. Not there, and
   a failed attempt before this one: `stale:gone`, the mark dropped, the
   hashes out of search, a stamp written; one info log line naming
   `occ files:scan`.
2. `stale:gone` among the Untrusted reasons in `fcias:status` and the
   admin status, in the 11 `.po` files.
3. A write or a scan that finds the file again queues it as any change
   does; the orphan purge takes the rows of a file whose filecache row is
   gone.
4. FAQ, *Troubleshooting*: files the filecache lists and the storage does
   not have, and what `files:scan` and `files:cleanup` do and do not
   remove.
5. Tests: unit for one and two failed attempts; integration for a file
   deleted on disk behind Nextcloud's back.

**Verification:** as Block 1.
**CHANGELOG:** Fixed: a queued file missing from its storage leaves the
queue, counted as untrusted (gone), instead of being retried for ever.
