## 1. Why: what is wrong today

All file/line references as of commit `1ee5f90`.

1. **The app starts working the moment it is installed, unconfigured.**
   `Version010000Date20260806100000::postSchemaChange()` calls
   `MetadataService::seedIndex()` ([lib/Service/MetadataService.php](../../lib/Service/MetadataService.php) ~838),
   a raw `INSERT…SELECT` that writes a `file-checksum-updated_at = 'pending:new'` index row for
   **every row in `oc_filecache`**. `ProcessPendingUpdates` then drains 50/minute and calls
   `HashCalculationService::processFile($id, 'new')`, whose no-rule fallback is
   `mode = auto, algos = ALL EIGHT` ([lib/Service/HashCalculationService.php](../../lib/Service/HashCalculationService.php) ~455).
   The only reason a fresh install does not hash the whole instance eight ways is an accident:
   `auto` recomputes only algorithms a file *already has*, and fresh files have none. The intent
   in that code is "no rule → all algorithms"; it is defused by the mode, not by design.

2. **No default rule exists at all on a fresh install.** `migrateToBands()` only *pins* a
   pre-existing global rule; a fresh instance has zero rules, so band 7 is empty and "no rule
   matched" is the *normal* case rather than the exceptional one.

3. **The queue mechanism depends on a universal row that exists only because a job keeps
   re-creating it.** `MetadataService::markPending()` is UPDATE-only *by documented contract* —
   "Does NOT create the row if it doesn't exist (seeding handles that)"
   ([lib/Service/MetadataService.php](../../lib/Service/MetadataService.php) ~431). A miss is a
   debug-level log and a silently dropped mark. `SeedPendingUpdates` re-runs `seedIndex()` every
   21 h (75600 s) purely to keep that assumption true. Consequences:
   - one metadata-index row per file exists to say *nothing* ("we have not looked yet");
   - `RuleProcessingJob`'s scan silently fails to mark any file whose row is missing
     (`getUpdatedAt()` → null → `markPending()` UPDATE matches nothing);
   - `pending:new` is a state whose entire meaning is "seeded, never considered".

   **Fact check that killed the "needed for joins" theory:** the duplicate-detection queries
   *explicitly exclude* the `updated_at` key
   ([lib/Service/MetadataService.php](../../lib/Service/MetadataService.php) ~618, `neq(meta_key,
   KEY_FILE_CHECKSUM_UPDATED_AT)`). Nothing joins against it. The row is load-bearing **only**
   because `markPending()` refuses to insert.

4. **CLI and background job disagree about "no rule matched".** Since commit `1ee5f90` the
   CLI's direct path skips unmatched files; the background `'new'` branch hashes them with all
   eight algorithms. Two components, same question, opposite answers.

5. **Hash erosion is invisible.** Since the RuleBands purge-on-write fix, a modified file whose
   governing situation no longer maintains hashes gets its stale hashes dropped
   ([lib/Listener/FileListener.php](../../lib/Listener/FileListener.php) ~151,
   `clearMetadata()`). Correct (decision #9: a wrong hash is worse than none), but with a
   disabled default rule the install-time backfill will erode file-by-file as users write, and
   today the only trace is a debug log line. Admins will perceive "my checksums are
   disappearing" with no way to see how much or why.

6. **Rules can only be managed through the web UI / REST.** `--ignore-rule=<id>` (Block 7)
   requires a rule ID that no CLI can show you. No occ rule management exists; the public PHP
   API (`ChecksumApi`) has no rules surface although REST `/api/v1/rules` does.

7. **The CLI's `generate` semantics are muddled.** `--algo` defaults to a hardcoded `sha1` and
   is comma-separated only; the collector checks hash *presence* only (never staleness); a
   collected file gets its **entire** requested algo set recomputed even for algorithms it
   already has; `--mark` hardcodes `pending:auto`; the rule's own `algos`/`mode` are never
   consulted on the direct path.

### Semantics summary: who answers "should this file be hashed?"

After this AP there is exactly one decision pipeline, used by every path:

```
resolve governing rule (findFirstMatchingRule, minus --ignore-rule set)
  → verdict include        → hash (algos/mode from rule, or CLI overrides per D8/D9)
  → verdict ignore         → skip, unless --with-ignored (CLI only)
  → verdict exclude        → skip, always (only --ignore-rule can change WHICH rule governs)
  → no rule matched        → skip, unless --unmatched=include|unmatched (CLI only)
```

Background job, event listeners, CLI direct path, and CLI `--mark` path all agree; the CLI's
extra flags are the *only* deviations and each names itself.

### Block 1 — Queue model rework *(core; [TASK]; everything depends on it)*

Implements D3, D4, and the erosion visibility half of D17.

1. **`MetadataService::markPending()` → upsert.** Try UPDATE first (common case); on 0 rows
   affected, INSERT the row (`file_id`, `meta_key = file-checksum-updated_at`,
   `meta_value_string = pending:<mode>`, `meta_value_int = 0`). Use the QueryBuilder for both
   legs (no raw SQL — portability). Race window (two inserts) is tolerable: unique-ish semantics
   come from the (file_id, meta_key) pair; catch the duplicate-key `Exception` and retry as
   UPDATE once. Remove the "seeding handles that" docblock contract; document the new one:
   *the row exists iff the file has ever been queued or hashed or eroded*.
2. **Retire `pending:new`.** Delete `PENDING_MODE_NEW` / `PENDING_NEW` constants and the whole
   `'new'` branch in `HashCalculationService::processFile()` (~437–476) including its
   no-rule → all-algos fallback. `processFile()` keeps working for `auto|missing|force|lazy`
   pending states. Grep for every `PENDING_NEW` / `'new'` consumer (ShowStatus counts by mode,
   `parseMode`, tests) and update.
3. **Delete `SeedPendingUpdates`** (class, `info.xml` `<job>` entry, its test). Note: NC does
   not auto-remove scheduled instances of a removed job class — the Block 2 migration must
   remove it from the joblist (`IJobList::remove(SeedPendingUpdates::class)` via a repair step;
   keep a string literal for the class name since the class will be gone).
4. **`eroded` state.** In `FileListener`'s purge-on-write path, replace `clearMetadata($fileId)`
   with a new `MetadataService::markEroded(int $fileId)`: strip the `file-checksum-*` hash keys
   (as `clearMetadata` does) **and** set the `updated_at` index row's string to `eroded`
   (upsert, same helper as markPending). Constant `MetadataService::STATE_ERODED = 'eroded'`.
   `clearMetadata()` itself stays for the force/lazy paths (they immediately re-queue, so the
   string gets overwritten by `pending:*` anyway).
5. **`MetadataService::countEroded(): int`** — indexed equality count for the status surface.
6. **Background no-rule answer = skip:** with the `'new'` branch gone, verify no remaining
   background path invents algorithms for unmatched files. (`ProcessPendingUpdates` drains only
   `pending:*` rows, which after this block are only ever written by rule-driven or
   CLI-driven marking, so this mostly falls out — assert it in tests.)

*Files:* `lib/Service/MetadataService.php`, `lib/Service/HashCalculationService.php`,
`lib/Listener/FileListener.php`, delete `lib/BackgroundJob/SeedPendingUpdates.php`,
`appinfo/info.xml`; tests: `MetadataServiceTest` (upsert both legs + duplicate-key retry,

(this was the silent no-op — write the regression test first).

### Block 3 — The `hash` command *(depends on B1; [TASK]; may split rename into own commit)*

Implements D6 (command half), D7, D8, D9, D10.

1. **Rename** `GenerateHashes` → `HashFiles` (class), `file-checksum-search:hash`,
   `setAliases(['fcias:hash'])`. **No `generate` alias** (D6) — update every doc/example in the
   same commit so no reference to the old name survives.
2. **`--algo|-a`** per D8. Parsing: flatten repeatable values through the existing
   comma-splitting normalizer; `auto` is a token, not an algorithm — validate real names
   against `HashCalculationService::SUPPORTED_ALGOS` and fail on unknowns (today unknown algos
   flow through silently — fix that here). Effective set per file: `auto ∈ set` →
   rule's algos ∪ explicit names; else explicit names only.
3. **`--mode|-m`** per D9. Per D21 the collection/staleness semantics are implemented in
   `HashCalculationService` (they already live there structurally; the *rules* for collection —
   effective algo set, staleness comparison, mode behaviour — must be expressed as service API
   taken by value objects, never re-derived in the command). Collector change: a file is
   collected if (a) it lacks any algorithm of
   its effective set, or (b) `mode=missing` and its `updated_at` int < file mtime, or (c)
   `mode=force`. Compute only the missing/stale algorithms under `missing`; the full effective
   set under `force`.
4. **`--unmatched|-u`** per D7. Interacts with the pipeline (§2 summary): `include` widens the
   allows-check; `unmatched` inverts it (only files with **no** governing rule). Under
   unmatched-only, `--algo=auto` (incl. default) → hard error before any work.
5. **`--mark|-k`** queues `pending:<--mode>`; under `--mode=force` that is `pending:force` (the
   drain's force semantics already exist). `--mark --unmatched=…` combinations mark per the
   same pipeline.
6. `RuleOverrides` grows `unmatched` handling (or a sibling field) so `allows()` stays the
   single decision point; `-v`/`-vv` reporting continues to work for all combinations
   (`[no matching rule]` + proceeding is now reachable via `--unmatched`).
