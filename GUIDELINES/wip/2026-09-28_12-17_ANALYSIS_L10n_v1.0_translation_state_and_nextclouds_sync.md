# ANALYSIS L10n v1.0: the app's translation state, and Nextcloud's sync

> **2026-09-28.** The research behind AP Translatable v1.0: two read-only
> research passes, reproduced verbatim below, their headings one level down.
> The first asks whether the app is translated through Nextcloud's Transifex
> automatically; the second measures what is wrapped for translation, what
> German coverage there is, and which languages to add. The second names
> scratch files (extraction scripts, the list of unwrapped strings,
> per-language key counts); they are not carried here, and its scripts can be

## 1. Nextcloud's translation sync, and what it asks of this app

### 1. The app's localisation state today

**Examples of unwrapped user-facing strings**

**Translation infrastructure**
- None exists: no `l10n/`, `.tx/`, `translationfiles/` or `.l10nignore`.
- `package.sh` and `.nc.publish.ignore` do nothing about l10n. `l10n/` is not excluded, so it would ship; `*.gitkeep` is excluded.
- `appinfo/info.xml` has no l10n settings. The translation tool would still extract its name, summary, description and the navigation `<name>Duplicates</name>` (`info.xml:91`).
- Loading needs no code. The server's `Util::addScript` and `addInitScript` inject the app's `l10n/` automatically (nextcloud/server stable33 `lib/public/Util.php:131–133, 157–161`).
- `js/` is not tracked in git.

### 2. How Nextcloud's Transifex sync works for outside apps

**The developer manual** ([translation page](https://docs.nextcloud.com/server/latest/developer_manual/app_development/translation.html); source `nextcloud/documentation` `developer_manual/app_development/translation.rst`)
- Line 14: tool-based translation "only supports repositories hosted on github.com".
- Lines 35–51: the `.tx/config` with `[o:nextcloud:p:nextcloud:r:{{APPID}}]`, plus `l10n/.gitkeep`.
- Lines 56–71: branches `main`, `master` and the last three `stableX`, or those named in `.tx/backport`.
- Lines 76–81: `.l10nignore`.
- Lines 95–100: invite `@nextcloud-bot` with write access, then open the "Request translations" issue.
- Lines 102–108: branch protection only works if the bot is admin.

**nextcloud/docker-ci**
- `translations/config.json`: repositories are opted in one by one as `"Owner Repo"` under job `app`. `"gino0631 nextcloud-metadata"` is at line 153. Nothing is automatic.
- `transifexSync.php` runs the container nightly on their `transifex-sync` host.
- `translations-app/handleAppTranslations.sh`:
  - clones `git@github.com:$1/$2` (l.20);
  - may commit and push "fix(l10n): Update Transifex configuration" (l.32–36);
  - on Saturdays fails if `max-version` < 31 (l.46–56);
  - pulls languages that are at least 5% translated (l.168);
  - commits "fix(l10n): Update translations from Transifex" and runs `git push origin $version` directly, with no PR (l.223–224).
- The bot identity is "Nextcloud bot <bot@nextcloud.com>" and its commits are GPG-signed (`translations/gitconfig`).
- `.github/ISSUE_TEMPLATE/---request-translations.md` adds these requirements:
  - the app is in the App Store (verified: apps.nextcloud.com/apps/file_checksum_search returns 200);
  - the author joins the Nextcloud project on Transifex;
  - the bot has write access and translated branches are not protected;
  - the app certificate is linked to the same repository. Certificate PR nextcloud/app-certificate-requests#1164 names `github.com/metaworx/file_checksum_search`, so this matches.
  - After that, the sysadmins run the first sync, the translation team (rakekniven) reviews, and a PR adds the repo to `config.json`.

**gino0631/nextcloud-metadata**
- Its `.tx/config` is exactly the template, with `r:metadata`.
- `l10n/` holds 188 `.js`/`.json` files. It has no `.l10nignore`.
- All of the last 100 commits touching `l10n/` are by `nextcloud-bot`, most recently on 2026-09-11.

### 3. Conclusion

Nothing is automatic. It is opt-in per repository, and gino0631 did the steps below.

**(a) Changes in this repository**
1. Wrap the strings. This is the bulk of the work: nearly all of the UI, plus PHP strings such as the search provider name.
2. Add `.tx/config` with `r:file_checksum_search`.
3. Add `l10n/.gitkeep`.
4. Add `.l10nignore` with `tests/`, `vendor-bin/`, `vendor/`, `js/` and `build/`. `tests/e2e` holds `.py` files, which the tool scans.
5. Run `bash translations/validateSyncSetup.sh metaworx file_checksum_search`.
6. Decide the contract status of `l10n/` (see (c)).

**(b) Steps only you can take**
1. Create a Transifex account and join the Nextcloud project.
2. Invite `nextcloud-bot` with write access to metaworx/file_checksum_search. `master` is currently unprotected (checked: "Branch not protected").
3. Open the "Request translations" issue in nextcloud/docker-ci.

**(c) Conflicts with how this repo is set up**
- **Mirror:** the bot pushes to GitHub `master`. The GitLab push mirror would force-push over that commit on its next push, and the bot would push again the next night. Tags are cut on GitLab, so translations would never be released. Workable fixes:
  - a GitHub workflow, triggered by the bot's push, that fast-forwards GitLab `master` (needs a GitLab token secret) before the next mirror push;
  - or making GitHub the source of `master`.
  - The bot always adds `master`, so `.tx/backport` cannot redirect it to another branch.
- **CHANGELOG:** the bot's commits carry no bullet and use the title format "fix(l10n): …", not `[TAG]`. `l10n/` is not in the contract's list of shipped-code paths, `config.ini` has no `project.shipped`, and CI does not run `changelog.sh check`, so nothing fails. Exempt `l10n/` explicitly, and add a "translations updated" bullet at each release cut.
- **CI:** `test.yml:9–10` runs on every push, so each bot commit runs the full matrix, Cypress included. `publish.yml` only runs on `workflow_call` or dispatch, so a bot commit does not publish anything.

**Alternatives**
- Run `translationtool.phar create-pot-files`, `tx push`/`pull` and `convert-po-files` from this project's own scheduled CI against a self-managed Transifex project, committing to GitLab.
- Use Hosted Weblate with its native GitLab integration, which avoids the mirror problem.
- Either way the app loses Nextcloud's translator community.

**Not verified from a primary source:** the mirror's `keep_divergent_refs=false` (taken from your brief); whether Nextcloud accepts an app whose canonical host is GitLab (the docs only require github.com); and the current free plans for open source at Transifex and Weblate.

## 2. What is wrapped, German coverage, languages to add

### l10n research: file_checksum_search

I changed nothing in the repository. Scratch files are in `/tmp/claude-1574/-home-mdr-projects-nc-file-checksum-search/30acdd28-c979-4a0c-a472-5018d895ae0f/scratchpad/l10n/`:
- `german-coverage.md`: every wrapped string with its call sites, plus notes on the unwrapped strings.
- `unwrapped-frontend.tsv`: 238 heuristic hits.
- `extract.py` and `unwrapped.py`: the extraction scripts.
- `stats_*.txt`: per-language key counts for the Nextcloud apps compared in section 4.

#### 1. What the app ships for translation
**Nothing.**
- There is no `l10n/` directory, no `translationfiles/`, no `.po`/`.pot` files and no `.l10nignore`. `git log --all -- l10n` is empty, so there never was one.
- No script in `package.json`, `composer.json`, `package.sh` or CI (`.github/`, `.gitlab/`) mentions l10n or translation, and there is no Makefile.
- If an `l10n/` directory were added, it would ship. `package.sh:392` rsyncs the whole tree minus `.nc.publish.ignore`, which does not exclude `l10n`, and `.gitignore` does not ignore it either.

#### 2. Every translatable source string
I extracted them with a script (`extract.py`). It finds `t`/`n`/`translate`/`translatePlural` calls in JS and Vue, and `->t`/`->n` calls in PHP, across line breaks. It parses literal arguments, including concatenated ones, and flags any argument that is not a literal. Spec and test-utils files are excluded. A plain grep gives the same result (21 call sites).
- **21 call sites, 17 unique strings, 0 plurals, 0 placeholders.** Every JS call uses app id `file_checksum_search`, so none looks up another app's translations.
- **PHP:** 1 string, `'File Checksum Index & Search'`, at `lib/Settings/AdminSection.php:46`, `lib/Settings/PersonalSection.php:46` and `templates/partials/settings-header.php:23`. The IL10N is injected as `$this->l10n`, and templates use `$l`.
- **Frontend:** 16 strings, all in the sidebar:
  - `src/sidebar.ts:23,45`
  - `src/sidebar-vue/ChecksumsSidebarTab.vue:142–260`
  - `src/sidebar-vue/components/RecalcButton.vue:47`
- `'Duplicates'` also covers the top-bar entry at `appinfo/info.xml:91`, because Nextcloud translates navigation names through the app's l10n.
- **Unwrapped strings are the norm.** The heuristic scan found 238 hits in 23 files. On top of those, grep found 20 toast texts, about 12 `result.error || '…'` fallbacks and about 17 band labels and descriptions in `src/rules-vue/bands.ts`. That is roughly **250–300 unwrapped UI strings against 16 wrapped ones**. The admin settings, personal settings, rules, duplicates and docs pages are entirely untranslated. Examples:
  - `src/settings-admin-vue/App.vue:360` "Automatic hashing is inactive."
  - `src/rules-vue/RuleForm.vue:485` "Save"
  - `src/duplicates-vue/components/DuplicateListing.vue:392` "No duplicate files found."
  - `src/duplicates-vue/App.vue:132–134` tab labels Mine/Others/Help
  - `src/settings-admin-vue/App.vue:238` `toastSuccess('Rule saved.')`
  - `src/components/LocationIcon.vue:45–52` titles
- **PHP also has unwrapped strings.** `lib/Search/HashSearchProvider.php:71` returns `'File Checksums'` (the Unified Search heading). About 55 API error strings sit in `lib/Controller/*.php` and `lib/Service/RuleDefinitionValidator.php`, among others. Several of them reach the UI verbatim through `result.error` / `data.error`.
- **Placeholders will be needed once these are wrapped.** Several unwrapped strings build text from variables, for example `Band ${rule.band}, position ${rule.position}` (`RuleRow.vue:92`) and `Granted ${…}` (`SudoTokensSection.vue:156`). They would need `{name}` placeholders when wrapped.

#### 3. German coverage
**There is no German file at all, neither `de` nor `de_DE`.** All 17 strings are missing in both. Stale entries, entries identical to the English source and placeholder mismatches are therefore 0 or not applicable. There is no register (du/Sie) to check.

This matters for rollout: Nextcloud's `Factory::findLanguage` only falls back from a user's `de_DE` setting to `de` through the browser's Accept-Language header. Otherwise it uses `default_language` or English. So both files should be shipped.

#### 4. Other languages to suggest
Evidence: per-language key counts from `gh api` for `nextcloud/groupfolders`, `nextcloud/files_antivirus`, `nextcloud/server apps/files` and `nextcloud/deck` (Deck's fullest language has 445 keys). I did not use user-base numbers or Transifex statistics; the size of each language community is general knowledge.
- de and de_DE, fr, pt_BR, tr, sk, zh_TW, zh_HK and en_GB are 100% in all four. Suggested order:
  1. **de + de_DE**: 100% everywhere; Nextcloud's home market.
  2. **fr**: 100% everywhere; large French public-sector community.
  3. **es**: 78/100/99.5%, Deck 411/445; very large speaker base. Deck alone carries 18 `es*` variants, but plain `es` is the one kept complete.
  4. **it**: 76/67/96%, Deck 416.
  5. **nl**: 72/100/99.5%, Deck 441.
  6. **pt_BR**: 100% everywhere; pt_PT is weaker (69/92/96%).
  7. **zh_CN**: 58/72/99.5%, Deck 441; zh_TW and zh_HK are fuller.
  8. **ja** or **pl**: ja 85/100/100% (Deck 384); pl 65/74/99.5% (Deck 441).
- **Variants Nextcloud splits:** de/de_DE, pt_BR/pt_PT, zh_CN/zh_TW/zh_HK, es plus es_MX, es_419, es_AR, es_EC and others, and en_GB. Some others carry a region code too (et_EE, lt_LT).

#### 5. Can translations still be maintained locally?
Yes, by what the repository shows.
- **Hand-written files would ship.** Nothing generates or overwrites `l10n/`, and `package.sh` would include it.
- **The frontend would pick them up automatically.** The app loads its scripts through `Util::addScript` (in the templates) and `Util::addInitScript` (`lib/Listener/BeforeTemplateRenderedListener.php:64`). Both inject `file_checksum_search/l10n/<lang>.js` on their own.
- **PHP would read the JSON.** It loads `l10n/<lang>.json`.
- **Format:** each language needs `<lang>.js` using `OC.L10N.register("file_checksum_search", {...}, "<pluralForm>")`, plus `<lang>.json` with the same content.
- **Nothing checks them:** `npm run lint` covers only `src/`, ECS covers `lib/`, `tests/`, `appinfo/` and `templates/`, and no CI job looks at l10n.
- **Two gaps in the contract:** `AGENTS.md` §1's list of shipped-code paths does not include `l10n/`, so the CHANGELOG rule in §3.3 would not cover translation-only commits unless `l10n/` is added to that list. And the vitest specs stub `translate` as identity, so no test would exercise a translation.

#### Summary
The app ships no translations at all. Only 17 strings are wrapped: the settings section title and the sidebar tab. Roughly 250–300 strings in the settings, rules and duplicates UI are not wrapped, and neither are the server error strings the UI displays. German coverage is 0% for both de and de_DE. Wrapping those strings is the prerequisite for any translation work. Once `l10n/*.js` and `*.json` files are committed, they would ship and load with nothing in the repository standing in the way.
