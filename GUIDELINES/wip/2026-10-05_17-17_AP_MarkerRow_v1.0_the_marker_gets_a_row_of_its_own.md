# AP MarkerRow v1.0: the marker gets a row of its own

## Discussion

- **The defect.** A file's marker — `pending:<mode>`, `stale:reset`,
  `stale:eroded` — lives in the string half of its
  `file-checksum-updated_at` index row. Nextcloud rewrites that row from
  the metadata document whenever any app saves the document
  (`IndexRequestService::updateIndex()` drops it and inserts the stamp
  alone), and the document does not hold the marker. So the marker is lost
  on the next save by Photos, blurhash, or anything else that writes
  metadata.
- **Reproduced on the test harness, NC 33 and NC 34 alike:** a hashed file
  is found by its sha1; `markStale()` writes `stale:reset` and the lookup
  finds nothing; another app writes a key of its own to the document and
  saves it; the marker is gone and the lookup finds the disowned hash
  again.
- **What it costs:**
  - `stale:reset` — `occ fcias:reset --hashes` disowns hashes and leaves
    their clearing to the drain. A save before the drain brings them back
    into every search, and the drain, which looks for `stale:reset`, never
    clears them.
  - `pending:<mode>` — a queued file leaves the queue. The rule sweep finds
    a changed file again by its stamp; a file queued by `force` or `lazy`,
    or by `MetadataListener` on Nextcloud's background event — whose own
    save follows at once and wipes the mark it just wrote — is not.
  - `stale:eroded` — the status page undercounts; the hashes are gone
    already, so nothing comes back.
- **Why the hash rows survive and the marker does not:** the hash keys are
  registered unindexed, and the app writes their rows itself, so
  Nextcloud's save never touches them. A key that is not in the document at
  all is equally out of its reach.

## Analysis

- **Options:**
  - **A — a row of its own** (proposed): the marker moves to an index row
    `file-checksum-state`, written and read by the app alone, never in the
    document. Nextcloud's save does not touch it; writing it stays one
    statement, so a reset over a whole instance stays an UPDATE per page of
    ids. The stamp row keeps the stamp and nothing else.
  - **B — an indexed key in the document**: Nextcloud would write the row
    from the document on every save, so it would survive too; but every
    marker would cost a metadata document save, and `markAllStale()` would
    rewrite every hashed document of the instance — the cost the marker
    was put in the index to avoid.
  - **C — write the marker again after every save**: Nextcloud raises no
    event after its save, only before it; nothing to hook.
- **What reads and writes the marker,** all in `MetadataService` but a few
  callers: `markPending()`, `markEroded()`, `markStale()`,
  `markAllStale()`, `clearStaleMarker()`, `clearQueueState()`,
  `upsertUpdatedAtString()` and `updateUpdatedAtString()`; `getMarker()`,
  `markersOf()`, `fetchPendingBatch()`, `fetchStaleBatch()`,
  `getPendingStats()`, `getStaleStats()`, `countByState()`,
  `countEroded()`, `exportStates()`; the stale filter of the lookup and the
  duplicates (`andWhereNotStale()`) and of the listing (`whereListed()`).
  Callers: `ProcessPendingUpdates`, `occ fcias:queue:drain`,
  `occ fcias:status`, `DuplicateService`, `RepairQuietStart`.
- **The stamp row's other meaning stays:** it exists for every file the app
  has considered — hashed, queued, eroded. A file queued before it was ever
  hashed gets its state row and a stamp row of 0, as `markPending()` gives
  it one today.
- **Existing markers move** in a repair step that runs inline, before the
  steps that read markers: a page of stamp rows with a string half at a
  time, each written as a state row and cleared from the stamp row. Markers
  are few — the queue and the disowned — so it costs a request little.
- **Gone files** lose the state row with the rest: Nextcloud's own delete
  drops every index row of the file, and `pruneAllIndexRows()` already
  matches `file-checksum-%`.
- **The listing's stale filter** becomes a lookup of the file's state row,
  counted per file like the hash rows (`(SELECT COUNT(*) …) = 0`), not
  `NOT EXISTS`, which MariaDB rewrites into a materialized join.

## Implementation Plan

### Block 1: the marker moves to a row of its own

1. `MetadataService`: `KEY_FILE_CHECKSUM_STATE = 'file-checksum-state'`;
   every writer and reader above on the state row; the stamp row keeps the
   stamp, and `markPending()` still gives a never-considered file a stamp
   row of 0.
2. The listing, the lookup and the duplicates leave out a file whose state
   row says `stale:`.
3. A repair step, `marker-row`, inline and cheap: existing markers moved
   from the stamp rows to state rows; idempotent.
4. Tests: unit for each writer and reader; integration for the
   reproduction — another app's save keeps the marker, the disowned hash
   stays out of the lookup, and the drain still clears it; a queued file
   stays queued; the repair step moves a marker and is a no-op the second
   time.
5. Measure the listing and the lookup on helioscloud.ddev.site, read-only,
   against 3.6 s and the lookup's current time.
6. Documents: `docs/FAQ.md` on the stamp row and the state row.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS,
Psalm.
