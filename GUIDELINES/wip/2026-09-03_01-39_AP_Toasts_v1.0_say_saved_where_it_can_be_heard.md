# AP Toasts v1.0: say "Saved." where it can be heard

> **Status: approved 2026-09-03, in execution.**

## Problem

Asked for: a toast when settings are saved, on the admin page (Save buttons)
and the personal page (saves on select), shown once the server has answered,
"Saved.", about five seconds.

Found: the app already calls `OC.Notification.showTemporary()` in nineteen
places — "Options saved.", "Algorithms saved.", "Rule saved.", every error.
Nextcloud 34's core bundles no longer define it (`dist/core-*.js` contain no
`showTemporary`), so every one of those calls has been a `TypeError` at the
end of a successful request, swallowed by the `uncaught:exception` handler in
`tests/e2e/support/e2e.js`. Nobody has seen a toast from this app on 34. The
personal preference never toasted success at all.

## Decision

- `@nextcloud/dialogs` ^7.5 (fits the installed `@nextcloud/vue` 9.9.0).
  Core ships the toast styles (`core/css/toast.css`); no stylesheet import.
- `src/toast.ts`: `toastSaved(text = 'Saved.')` (success, 5 s),
  `toastSuccess(text)` (success, 5 s), `toastError(text)` (error, library
  default, stays until dismissed on hover as Nextcloud's do). One module, so
  specs mock one module instead of stubbing `window.OC.Notification`.
- Every `OC.Notification.showTemporary` call goes through it: success texts
  become "Saved." where a setting was saved (permissions, algorithms,
  preference — the last one gains its missing success toast); rule actions
  keep their specific texts ("Rule saved.", "Rule deleted.", enabled/disabled,
  re-apply queued, banner acknowledged) via `toastSuccess`; failures via
  `toastError`.
- Toasts fire after the response is parsed and `success` is confirmed, never
  optimistically.
- `OC` window shims shrink to `requestToken` where that is all that is left.

## Scope

One block, one commit. Files: `package.json`/lock, `src/toast.ts` (new),
`settings-admin-vue/App.vue`, `PermissionSection.vue`, `AlgorithmSection.vue`,
`settings-personal-vue/App.vue`, `PreferenceSection.vue`; specs of the same
(`vi.mock` the helper; `AlgorithmSection.spec` asserts `toastSaved` after a
successful PUT and `toastError` after a refused one; a `PreferenceSection.spec`
is added for the same two paths). CHANGELOG bullet.

Verification: lint, vitest, build; live on instance 34 — save on each of the
three sections and confirm a toast in the browser is the user's; headless I
confirm the built bundle imports the library and that the e2e suite stays
green (rules-admin, rules-personal, status).

## Open decisions

- The `uncaught:exception` handler in the e2e support file hides exactly this
  class of defect. Narrowing it (to the known Nextcloud noise it was added
  for) is a separate change; recommended.
