# AP HashFilter v1.0: filter the listing by hash

> **Status: proposal, 2026-09-03.** A filter on the duplicate listings, so a
> hash in hand finds its group without reading the page. Rulings from the
> review that asked for it are folded in below.

## What it is

A **Hash** field beside *Algorithm*, *Min* and *Limit*, with a **Search
anywhere** checkbox next to it. Empty, nothing changes.

Matching, in the order the review named:

- **exact** — the whole value, first in the results;
- **prefix** — groups whose hash starts with what was typed, after the exact
  ones;
- **anywhere** — with the checkbox on, the value found anywhere in the hash.

Both listings get it: *Mine* and *Others* share `DuplicateListing`, so one
implementation serves both and each keeps its own filter, as it keeps its own
algorithm and page.

## The long-hash problem, and the ruling

`oc_files_metadata_index.meta_value_string` holds at most 63 characters
({@see MetadataService::META_VALUE_STRING_MAX_LENGTH}); a SHA-512 is 128. A
term longer than 63 therefore cannot be compared whole in the index.

**Ruled: reuse the route that already solves this.**
`MetadataService::queryByHash()` joins the metadata document and, for a
truncatable hash, adds `m.json LIKE '%<hash>%'` server-side — narrowing before
the row is sent, with `confirmFullHash()` remaining the authority because the
pattern can over-match but cannot exclude. `queryDuplicates()` takes the same
two-part shape rather than inventing a second one.

So: the index is compared on the truncated term, and a long term additionally
matches the document. `verifyTruncatedDuplicateGroups()` already splits a
group whose members differ past character 63, so an over-match is corrected
before anyone sees it.

## Blocks

1. **[TASK] The filter in the query.** `queryDuplicates()` takes `$hash` and
   `$anywhere`. Wildcards in the term are escaped (`escapeLikeParameter`) and
   LIKE patterns are built in PHP, so no `||`/`CONCAT` divergence reaches the
   SQL — it stays backend-agnostic, as everything here must. Ordering puts
   exact matches before prefix matches, then the existing count order. The
   parameter travels the chain that already exists: `DuplicateService` →
   `HashIndexService` → `ChecksumApi` → the controllers. Unit tests per
   matching mode, including a long hash reaching the document clause.
2. **[TASK] The control.** A text field and the *Search anywhere* checkbox in
   `DuplicateListing`, so both tabs have it; the listing reloads on change,
   debounced, and resets to the first page. Vitest for the state, and the
   `duplicates` e2e filters a group it planted.
3. **Docs.** User guide (the field and the checkbox), `docs/api-v1.md` and the
   OpenAPI for the new query parameters.

## Open decisions

1. Whether the public API's `/api/v1/duplicates` twin takes the parameters
   too — recommended yes, for parity, and it costs nothing once the chain
   carries them.
2. Case: hashes are stored lower-case, so the term is lower-cased before
   matching — recommended, and it makes a pasted upper-case digest work.

## Gate

Per block: PHP suite; for block 2, `npm run lint` + `npx vitest run` +
`npm run build` + the `duplicates` e2e; full e2e at the end.
