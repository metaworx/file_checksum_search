# AP E2ETests v1.0: Rebuild and extend e2e suite

> **Status: preliminary — not yet approved.** Written from an analysis-only session; nothing under
> `tests/` has been changed. Independent of the other three APs; land it first — the CI e2e job is
> red today.

## Discussion

- **CI is failing now, not at release time.** `.github/workflows/test.yml:190-199` runs
  `cypress-io/github-action@v6` with `spec: tests/e2e/**/*.cy.js` on every matrix run. Verified
  empirically against instance 34 (2026-08-29): `rules.cy.js` fails **4/4** — its intercepts stub
  the removed `/settings/cron/definitions|save|delete|toggle` endpoints (tests/e2e/rules.cy.js:23-26),
  so the page loads real data from `/api/v1/rules` and the asserted strings
  (`No additional rules.`, rows for `/test-dir` etc.) never appear; `checksums.cy.js` still passes
  **3/3**. One failing spec fails the job, so every push is red on the e2e leg.
- **Text-free selectors are a hard requirement.** Only `src/sidebar-vue/*` and `src/sidebar.ts` use
  `t()`; there is no `l10n/` directory yet. When translation lands, every `cy.contains('Enable')`-style
  assertion breaks. All new specs assert on `data-*` attributes and ids
  (`[data-action=…]`, `tr[data-placeholder=…]`, `[data-band=…]`, `#fcias-*`) and on API payload
  fields, never on visible English — the one deliberate exception is Nextcloud-core chrome
  (login page, apps list), which the app does not translate.
- **Stub-vs-live**: the old rules spec stubbed everything and thereby tested nothing once the
  endpoints moved. The rebuilt rules specs go **live-first** (real `/api/v1/rules` calls, occ-based
  reset), with `cy.intercept` kept only where determinism needs it (provider-missing, only-matching
  filter). API-level behaviour (status codes, permission refusals) is asserted with `cy.request`
  directly — cheaper and not brittle.

### Block 2 — support commands (occ reset + OCS helper + user seeding)

3. In `tests/e2e/support/e2e.js` add:

```js
// Reset the rule set to the shipped state: delete everything, let the
// repair step recreate the two disabled defaults. occ is the only honest
// reset — the REST surface refuses some deletions by permission design.
Cypress.Commands.add( 'fciasResetRules', ( occ ) => {
	cy.exec( `${ occ } fcias:rules:list --output=json`, { failOnNonZeroExit: false } )
		.then( ( { stdout } ) => {
			let rules = []
			try { rules = JSON.parse( stdout ) } catch ( e ) { /* empty list */ }
			for ( const rule of rules ) {
				cy.exec( `${ occ } fcias:rules:delete ${ rule.id }`, { failOnNonZeroExit: false } )
			}
		} )
	cy.exec( `${ occ } maintenance:repair` )
} )

// Authenticated OCS request; url is relative to the app's OCS base.
Cypress.Commands.add( 'ocs', ( { method = 'GET', url, body, user, password, failOnStatusCode = false } ) => {
	return cy.request( {
		method,
		url: `/ocs/v2.php/apps/file_checksum_search${ url }`,
		body,
		auth: { user, pass: password },
		headers: { 'OCS-APIRequest': 'true', Accept: 'application/json' },
		failOnStatusCode,
	} )
} )

// Ensure alice and bob exist (CI starts with only admin).
Cypress.Commands.add( 'fciasEnsureUsers', ( occ ) => {
	for ( const u of [ 'alice', 'bob' ] ) {
		cy.exec( `OC_PASS=SecretPass123! ${ occ } user:add --password-from-env ${ u }`,
			{ failOnNonZeroExit: false } )
	}
} )
```

   (Exact `rules:list --output=json` flag name to be confirmed against
   lib/Command/Rules/ListRules.php during implementation — the changelog says it "speaks JSON for
   scripting".)
