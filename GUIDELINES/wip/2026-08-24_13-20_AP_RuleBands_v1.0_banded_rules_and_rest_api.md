# AP RuleBands v1.0: Banded rule priority, exclude rules, and the /api/v1 rules REST API

**Origin:** design discussion of 2026-08-24, evaluating
[`2026-08-22_04-18_AP_SuggestedFeatures_v1.0_design_new_features.md`](2026-08-22_04-18_AP_SuggestedFeatures_v1.0_design_new_features.md)'s
Feature 2 after the drag-and-drop reorder commit (`d548d86`) exposed two ordering flaws.
This AP **supersedes** that AP's Feature 2 design (rule `type` + flat-list ordering) and the
cross-band drag behaviour shipped in `d548d86`.

---

## 1. Why this AP exists

Three findings from the evaluation session, in increasing severity:

1. **The reorder shipped in `d548d86` has a sandwich bug.** A personal user whose own rules
   straddle a locked rule (`[mine-A, locked, mine-B]`) can submit a legal-looking permutation of
   their *own* IDs that lands `mine-B` in front of the locked rule — outrunning it in
   first-match-wins evaluation. The permutation check validates set membership, not boundary
   crossings.
2. **A user can already edit an instance-wide rule.** `canUserMutateRule()` allows scope-`all`
   rules; `savePersonalRule()` preserves `userScope = 'all'` on edit. A non-admin can change the
   path/mode/algos of a non-enforced global rule *for every user*, no ordering trick needed.
3. **The global rule inverts the original design spec.** The spec was: higher order value =
   higher priority, global rule = priority 0 = **last resort**. The implementation stored it at
   slot 0 of an array evaluated front-to-first-match — so the `**` catch-all matches everything
   first and **every additional rule is dead** while it is enabled. The docblock ("first =
   highest priority") codified the inversion.

The fix for all three is structural, not validational: rule position becomes a derived property
of *what kind of rule it is* (bands), users only ever order rules inside their own band, and the
catch-all lands where the spec always meant it to be — last.

**Acknowledged consequence:** the moment the inversion is fixed, every additional rule on an
instance with an enabled global rule goes from dead to live. Nothing is published; no migration
path for external users is needed. ("Finally", per the user.)

## 2. The band model (all decisions confirmed by the user, 2026-08-24)

Rules are evaluated top to bottom, **first match wins**, in seven bands. Within the enforced
half, **specific beats general** (user-confirmed over the earlier general-first draft), so an
admin can express "enforce sha256 everywhere, sha512 for alice" — under general-first the
alice rule would be silently dead. Every enforced rule is admin-authored, so this ordering
costs nothing in safety and buys exception power.

| Band | Contents | Authored by | Ordered by | User sees |
|------|----------|-------------|------------|-----------|
| 1 | user-scoped, enforced | admin | admin | read-only |
| 2 | group-scoped, enforced | admin | admin | read-only |
| 3 | global, enforced | admin | admin | read-only |
| 4 | user-scoped, not enforced | user **or admin** | the owning user (admin may too) | **editable** |
| 5 | group-scoped, not enforced | admin | admin | read-only |
| 6 | global, not enforced | admin | admin | read-only |
| 7 | the pinned `**` global default | admin | (single rule) | read-only |

One sentence explains the whole list: *enforced beats unenforced; within each half, specific
beats general; the catch-all is last.*

Properties that fall out by construction:

- No user rule can ever outrun an enforced rule (bands 1–3 precede band 4).
- A user rule overrides exactly the **defaults** (bands 5–7) — which is what non-enforced means.
- The `d548d86` sandwich bug is impossible: band 4 is contiguous, there is nothing locked inside
  it to hop over. Reorder needs no boundary check at all.
- Finding 2 closes: a user's write surface is band 4, scope = self, full stop. Editing
  scope-`all` or group rules from the personal page is gone.
- **Band 4 rules created by an admin for a user are the user's to edit/reorder/delete**
  (confirmed: this is the "admin gives support" case). Admin authorship confers nothing; the
  enforced flag is the only lock.
- Toggling `admin_enforced` (admin-only) moves a rule between bands 1↔4 / 2↔5 / 3↔6. Band is
  **always derived from (scope, enforced, pinned) — never stored.**
- Band 4 rules of different users never compete (scope filter), so only same-owner relative
  order matters there.

### 2.1 Group rules (in scope for v1, user-confirmed)

New scope kind. `userScope` stays a single string field for zero-migration compatibility:
`'all'` | `'group:<gid>'` | `'<uid>'` (NC user IDs cannot contain `:`; the prefix is
unambiguous). New machinery, honestly sized as the largest single item in this AP:

- `findFirstMatchingRule()`: `IGroupManager::isInGroup($ownerUid, $gid)` per group-scoped rule.
- `resolveUsers('group:<gid>')`: expand members via `IGroupManager`.
- `IGroupManager` returns as a `RuleService` dependency (removed in the facade-drop commit;
  it comes back for scope, not permissions).
- Dialog gains a group picker (a groups list already ships in the admin-options payload).
- Multi-group conflicts resolve by within-band order — banding answers this for free.

### 2.2 The pinned global default (band 7)

Kept special: single, undeletable, pinned last (user-confirmed). **Recommendation adopted
unless overridden: it stays disable-able via the normal `enabled` toggle** — the alternative
("un-disablable, disable by emptying algos") would overload the existing "at least one
supported algorithm is required" validation into a semantic and is a hack. Disabling the
default is a legitimate admin choice ("only rule-matched files get hashes"). Marked by a
`pinned: true` flag assigned during migration from today's slot 0.

### 2.3 Priority display: `<band>.<order>`, 1 = highest

User-confirmed: the old "higher value = higher priority" spec is itself reverted — **1 is the
highest priority** ("it's my #1 priority"). The table renders in evaluation order, top wins,
numbered `<band>.<position>`: `1.1` beats everything, the global default is `7.1` at the
bottom. Ascending numbers down the page, no inversion between display and evaluation anywhere.

## 3. Exclude rules (folded in from SuggestedFeatures Feature 2 — same AP, separate commit)

Included here rather than later because they touch exactly the surfaces this AP rewrites
(matching, dialog, row rendering); deferring means a second pass over identical code.

**Semantics — settled: terminal verdict, uniform across all bands.** An exclude is not control
flow ("stop scanning… how far?"), it is a verdict like a firewall DROP: an include resolves the
file to "hash with these algos/mode", an exclude resolves it to "nothing". First match wins,
the file is decided, done. Band position supplies all authority semantics:

- Enforced exclude (bands 1–3): a mandate — nothing below, including user rules, can hash the
  matched files.
- User exclude (band 4): opts the user's files out of the defaults below — legitimate by
  definition (defaults are the overridable half). If the admin objects, the remedy already
  exists: enforce the rule.
- Default exclude (bands 5–6): overridable by a user include in band 4 (scanned first).

**Reserved, not built:** a "pass"/fall-through verb (firewall `RETURN` — "skip my rules here,
let the defaults apply"). If ever needed it is a third rule type, never a variant of exclude.

Mechanics: `type: 'include' | 'exclude'` on the rule (absent = include, zero migration).
`findFirstMatchingRule()` returns null on an exclude match; `evaluateRules()`' batch path adds
an exclude rule's matches to the existing exclusion set and marks nothing — the mechanism
already exists. Dialog: when type = exclude, algos/mode are hidden (nothing is computed).

**Open decision — confirm before Block 3 executes:** what happens to *existing* hashes of a
file that newly matches an exclude? **Recommendation: stop maintaining, do not purge** — least
destructive, reversible by removing the rule, and a purge is already possible via CLI if
wanted. The alternative (active deletion of stored hashes on exclusion) is a data-destroying
side effect of a rule edit and should not be implicit.

## 4. REST API (user-confirmed namespacing)

The `/settings/cron/*` vs `/personal/rules/*` split dies **because it encodes surface where
permission belongs**: an admin-group member on their personal page currently gets the scoped
controller and cannot do admin things there. One resource, server answers per caller.
`/api/v1/` has no external consumers (never published) — the contract may change freely, and
these endpoints become documented contract in `docs/api-v1.md` + the OpenAPI spec.

```
GET    /api/v1/rules                    caller-scoped, banded, annotated (band, canEdit)
POST   /api/v1/rules                    create — scope/enforced validated per caller capability
PUT    /api/v1/rules/{id}               update (toggle = update of `enabled`; no separate
                                        toggle endpoint — the UI holds the full rule anyway)
DELETE /api/v1/rules/{id}
PUT    /api/v1/rules/order              { band, ownerId?, orderedIds } — permutation within
                                        one band (band 4: one owner's rules)
GET    /api/v1/settings/status          (moves from /settings/status; admin)
GET    /api/v1/settings/permissions/{key}   key: rule_editing now; manual_recalc,
PUT    /api/v1/settings/permissions/{key}   api_access later (Features 6/7) — own commit
(reserved) /api/v1/preferences/{key}    per-user prefs; first tenant: Feature 5's
                                        drift-notification opt-out
```

Notes: mutations keep CSRF protection (no `NoCSRFRequired`); rules endpoints are
`NoAdminRequired` with capability enforced in the service layer; `/settings/*` admin-only;
none of these are rate-limited (cheap config ops — document as such). `/admin-options` dies
un-mourned.

Reorder authorization, restated for the banded world: admin may reorder within any band
(including any user's band-4 segment); a user may reorder only their own band-4 rules. The
submitted list must be exactly a permutation of that band(-segment)'s IDs.

## 5. Implementation blocks

Each block = at least one commit; **every commit carries a CHANGELOG `[Unreleased]` entry —
no exemptions** (user directive, stricter than COMMIT.md §4.3). Concrete commit messages are
drafted at execution time per COMMIT.md.

**Block 1 — Remove the dead crontab-snippet endpoint** *(first, own commit — user-confirmed)*
Delete `SettingsController::getCrontabSnippet()`, its `routes.ts` entry, and its two tests
(the ones needing the global `OC` class — the local suite's unrunnable count drops from 3
to 1). Rationale mirrors the legacy-API drop: restore all or nothing if Feature 8 revives it.

**Block 2 — Band model core in `RuleService` + migration**
Scope parsing (`all` / `group:<gid>` / uid), band derivation `band(scope, enforced, pinned)`,
the band-sorted storage invariant (stable re-sort on every write; storage stays one JSON array
in `IAppConfig`), `IGroupManager` dependency for group matching/resolution, matching rewritten
to banded order (this is the inversion fix — slot-0 `**` becomes the pinned band-7 tail via
one-time migration of the stored array, preserving relative order within each derived band),
`canUserMutateRule()` tightened to band-4-own-scope, reorder rewritten as
within-band-permutation (deleting the `d548d86` cross-band splice logic and its sandwich bug).
Tests: band derivation table, migration fixture (slot-0 default → band 7, mixed rules
re-partitioned), matching order across bands incl. group membership, specific-beats-general
within enforced half, reorder rejections (wrong band, foreign owner, non-permutation),
user-mutation tightening (scope-`all` edit now rejected — regression test for finding 2).

**Block 3 — Terminal exclude rules** *(separate commit; confirm §3's open decision first)*
`type` field + validation, verdict semantics in `findFirstMatchingRule()` (null on exclude
match) and `evaluateRules()` (exclude matches feed the exclusion set, mark nothing). Tests:
enforced exclude beats user include below; user exclude suppresses defaults but not enforced
rules above; default exclude beaten by user include; legacy no-`type` rules behave as include.

**Block 4a — `/api/v1/rules` controller** — new controller, caller-scoped capability, old rule
routes on both settings controllers deleted, `routes.ts`, `docs/api-v1.md` + OpenAPI. Tests:
same caller-capability matrix as Block 2 but at HTTP level (401/403/400/permutation-reject),
admin-vs-user listing shapes.
**Block 4b — `/api/v1/settings/*`** *(own commit — user-confirmed)* — permissions/{key} GET/PUT
replacing admin-options, status move, old routes deleted, docs. `PermissionService` needs no
change (already keyed). Tests for key validation (unknown key → 400, from the existing
`InvalidArgumentException` behaviour).

**Block 5 — Frontend: single banded table + dialog**
One color-coded table replaces the global/additional split (kills the shared-colgroup hack):
band = row colour + thin block separators, `<band>.<order>` priority column, drag constrained
to the row's own band (block-contiguous by construction), pinned 7.1 row undraggable/undeletable.
Dialog: Scope control (global/group/user, contextual pickers) + Enforced toggle + live
"→ band N" indicator; band never stored. Optional three-button "Add …" shortcuts pre-fill
scope. Exclude type selector hides algos/mode. Personal page: applicable bands 1–3 read-only
above, own band 4 editable, applicable 5–7 read-only below; creation fixed to "User rule (not
enforced)". Composables move to the new endpoints. Vitest: band rendering/colour, drag stays
in band, pinned row immovable, dialog band indicator, exclude field hiding, personal read-only
bands. May split into table+reorder / dialog commits at execution time.

**Block 6 — Docs**
README Hash Generation Rules rewritten around bands + `<band>.<order>` + exclude verdicts
(including the "pass is reserved" note), FAQ, HELP, final api-v1/OpenAPI cross-check.

**Deferred, recorded:** keyboard reorder (Ctrl+↑/↓ — frontend-only, focus-retention caveat);
the "pass" verb; `manual_recalc`/`api_access` permission keys (Features 6/7 land on Block 4b's
endpoint pattern); `/api/v1/preferences` first tenant (Feature 5).
