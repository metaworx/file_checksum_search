# AP Vocabulary v1.3: stop hand-copying the composable surface

> **Status: approved 2026-09-02.** Follows v1.2 (`3497521`, `a6cffdf`), which
> renamed the drifted keys. This removes what let them drift.

## Discussion

The two settings composables do compose the same code — both call
`useRules(scope)`, and all CRUD lives there. What is duplicated is the **manual
re-export list**: `useRules()` already returns

```ts
{ ...toRefs(state), load, saveRule, deleteRule, toggleRule, applyRule, reorderSegment }
```

and its `State` holds all thirteen keys the two shims re-list by hand — thirteen
retyped in `usePersonalSettings`, fifteen in `useAdminSettings`, every one of
them handing a value straight back. Two hand-maintained copies of one list is
exactly how they drifted into `definitions` against `rules`. v1.2 fixed the
symptom.

What each shim adds once the list is gone:

| | Real content | Aliases |
|---|---|---|
| `usePersonalSettings` | none | `canEditAny`←`canCreate`, `loadRules`←`load` |
| `useAdminSettings` | status block, idle banner | `loadRules`←`load` |

`loadRules` is aliased in both because `useRules` calls it `load`, which says
nothing at a call site that also has `loadStatus`. Renaming it there removes the
last reason either list existed.

## Analysis

### No collisions

`useAdminSettings`' own `toRefs(state)` contributes `status`, `statusLoading`,
`statusError` and `lastUpdated`. `useRules`' thirteen are `rules`, `canCreate`,
`supportedAlgos`, `modes`, `types`, `availableUsers`, `availableGroups`,
`groupFoldersAvailable`, `groupFoldersLabel`, `availableGroupFolders`,
`availableStorages`, `loading`, `error`. Disjoint.

The spread also exposes keys the admin page does not read (`canCreate`,
`loading`). Harmless: this is a composable, not an API surface.

### The one alias worth keeping, moved

`canEditAny` is a `RuleTable` **prop** name, used at three sites in the personal
page and in `RuleTable.vue` itself. The prop keeps its name — it gates a message
and the add button, and "can edit any" is what it means there. The page binds it
from `canCreate`, so the alias lives at one attribute binding instead of in a
file of its own.

### Test coverage — one case must move, not go

`usePersonalSettings.spec.ts` has three cases. Two are already covered by
`useRules.spec.ts`: "asks for the caller's own view" by *requests the view it
was created for* (which asserts both scopes), and "loads rules and the
create-capability flag" by *loads rules and the capability flag*.

The third — `error.value` set to `'Failed to load rules.'` after a rejected
load — is **not** covered there. `useRules.spec.ts` asserts an error result from
`toggleRule`, never `error.value` from a failed `load`. That case moves into
`useRules.spec.ts`; deleting it would lose the only coverage of that path.

## Implementation Plan

### Block 1 — `load` → `loadRules` in `useRules` · `[TASK]`

1. Rename the function and its returned key in `useRules.ts`, including the
   internal reload calls after a successful mutation.
2. Follow in `useRules.spec.ts`, `usePersonalSettings.ts`, `useAdminSettings.ts`.
3. `npm run lint`, `npm test`, `npm run build`.

### Block 2 — spread in `useAdminSettings` · `[TASK]`

4. Replace the fifteen re-listed keys with `...useRules('all')`.
5. Same three commands.

### Block 3 — delete `usePersonalSettings` · `[TASK]`

6. `settings-personal-vue/App.vue` calls `useRules('own')` directly;
   `canEditAny` becomes `canCreate` at its three sites, and the `RuleTable`
   binding becomes `:can-edit-any="canCreate"`.
7. Move the failed-load error case into `useRules.spec.ts`; delete
   `usePersonalSettings.ts` and `usePersonalSettings.spec.ts`.
8. Same three commands.

**Verification (all blocks):** full e2e suite green — `rules-personal.cy.js`
drives every path the deleted shim served, so a mis-wired `useRules('own')`
fails six tests rather than none. `grep -rn usePersonalSettings src/` empty, and
the vitest count drops by exactly the two retired duplicate cases.
