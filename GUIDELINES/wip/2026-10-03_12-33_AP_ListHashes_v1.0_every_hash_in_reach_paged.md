# AP ListHashes v1.0: every hash in reach, paged

## Discussion

- **The ask.** The kunstarchiv project syncs its image database (Augias)
  with this app's checksums, joining on the file's path. Today it can only
  ask hash by hash (`lookup`). It wants one listing of every file's hashes,
  page by page, to load into SQL Server.
- **Settled with the user, 2026-10-03:**
  - the route is `GET /api/v1/hashes`, with a `/sudo/` twin, and the PHP
    method `ChecksumApi::listHashes()`;
  - one entry per file; `hashes` is an object keyed by algorithm, and
    `updated_at` belongs to the file, since the app keeps one stamp per
    file, not per algorithm;
  - `/file/{id}/hashes` takes the same shape, so the API has one;
  - paging by a cursor on the file id: `after`, answered by `next`;
  - `estimated_total` when no `after` is given, `limit=0` included, which
    makes `limit=0` the count request;
  - the `/sudo/` twin gives the absolute path on the server, as
    `/sudo/lookup` does, for external mounts;
  - its own rate limit, above `lookup`'s 60 per minute.
- **Not in this plan:** a change feed that reports moves, renames and
  deletions (`/hashes/changes`). The filecache records no time for a move:
  `Cache::moveFromCache()` rewrites the path, name, parent and storage of
  the moved row and of everything below it, and sets no timestamp, and the
  propagator only touches the ancestors. Such a feed needs a journal of the
  app's own (a rename listener, tombstones, pruning), and waits until the
  nightly full listing proves too slow.

## Analysis

- **The contract.**

  ```
  GET /api/v1/hashes?algo=<algo>&limit=<0..1000>&after=<fileid>&since=<time>
  GET /api/v1/sudo/hashes?…&users[]=<uid>&groups[]=<gid>&localPath=1
  ```

  ```json
  {"files": [{"fileid": 185323,
              "path": "/Fotos/…/GPZ B 0001.01.001.jpg",
              "name": "GPZ B 0001.01.001.jpg",
              "owner": "kunstarchiv",
              "location": "/kunstarchiv/files/Fotos/…",
              "localPath": "/store/data/kunstarchiv/files/Fotos/…",
              "updated_at": "2026-09-02T15:17:00+00:00",
              "hashes": {"sha256": {"algo": "sha256", "hash": "d3e1c5…"}}}],
   "next": 185323,
   "estimated_total": 57459}
  ```

  - `limit`: 500 by default, 1000 at most; 0 returns no files.
  - `after`: the last file id already received; 0 by default.
  - `since`: files whose `updated_at` is at or after it, ISO 8601 or unix
    seconds.
  - `algo`: only files with a hash in that algorithm, and only that one in
    `hashes`.
  - `next`: the file id to pass as `after`, while entries remain; `null`
    when none do. With `limit=0` it echoes `after`, so a count is never
    read as the end.
  - `estimated_total`: the files the whole listing holds under the same
    filters, counted when no `after` is given. Approximate: files come and
    go during a run.
  - `updated_at`: ISO 8601, as the rest of the API; null for a file whose
    hashes carry no stamp.
  - `hashes`: an object, `{}` when empty. PHP encodes an empty array as
    `[]`, so it is built as an object.
  - `path`: the file as the first account in reach that holds it sees it,
    with a leading slash, as `lookup` gives it. With every account in reach
    and no account named, the owner's view; for a file no account owns, its
    path in its storage, which `location` names.
  - `localPath`: on the twin, with `localPath=1`, for a sudoer only, also
    when `users[]`/`groups[]` narrow the set. `/sudo/lookup` refuses it
    whenever the scope is a list, which a sudoer's narrowed set is too; the
    question it asks is who the caller is, not how wide the scope is. A
    group admin asking gets 403. Null for a file that is not on this
    server's disk: an object store, a remote mount, a share.
- **What `/file/{id}/hashes` changes.** `hashes` becomes the object above,
  and `updated_at` moves from each entry to the response. The same for
  `ChecksumApi::getHashesByFileId()`, `getHashesByFile()` and
  `getHashesByPath()`. A caller reading the list breaks. Below 1.0.0 that
  ships in a minor release, under `### Changed` (`docs/api-v1.md`,
  "Versioning & Compatibility"). The app's own reader is the sidebar:
  `useSidebarHashes.ts`, and `crossAccountLink.ts`, whose "the preferred
  algorithm's, else the first row's" becomes a key, else the first key.
- **Where the listing reads from.**
  - **The selection comes from the index:** a file is listed when it has
    index rows for a hash key (`file-checksum-hash-<algo>`). A reset hides
    a file's hashes from search by removing those rows while the document
    keeps the values, so listing from the documents alone would show what
    `lookup` hides.
  - **The values come from the documents:** the index truncates values to
    63 characters, and a SHA-256 is 64. One batched read per page,
    `getMetadataForFiles()`, as the duplicates listing does.
  - **`since` is cheap:** `file-checksum-updated_at` is an indexed integer.
  - **The reach:** the mounts of the accounts in reach, storage and root,
    as `ReachResolver` gives them, so a share counts only for its subtree.
    Ordered by file id, one row past the limit to know whether `next` is
    null. `IQueryBuilder` only, for every supported database.
  - **The cost is the path**, not the query. `lookup` asks `getById()` per
    file and per account; a page of 500 should derive paths from the
    reach's mounts in one pass instead, and is measured.
- **Rate limit.** 300 per minute on both routes, each counted on its own.
  `ratelimit_overwrite` changes it per route; Nextcloud's brute-force
  allowlist lifts it for an address when `bruteforcesettings`'s
  `apply_allowlist_to_ratelimit` is on. Both go into `docs/api-v1.md`'s
  "Rate Limiting". A limit the app could switch at runtime
  (`ARateLimit::shouldApply()`, NC 34.0.2 and the NC 33 line) waits.
- **Coordination.** The other session may plan an AP DbVersion that edits
  `docs/api-v1.md`, `docs/api-v1-openapi.yaml` and `CHANGELOG.md`; the order
  of those edits is agreed with it before Block 1 starts.
- **The release.** One Changed and one Added bullet: a minor, 0.22.0.

## Implementation Plan

### Block 1: a file's hashes, keyed by algorithm

1. `ChecksumApi::getHashesByFileId()`, `getHashesByFile()` and
   `getHashesByPath()` return `hashes` as an object keyed by algorithm,
   `{}` when empty, and `updated_at` once, beside `fileid`.
2. `/api/v1/file/{fileId}/hashes` and its `/sudo/` twin pass that on.
3. The sidebar reads the object: `useSidebarHashes.ts`,
   `crossAccountLink.ts`, their types and specs.
4. Docs: the OpenAPI's `HashEntry` and the per-file response,
   `docs/api-v1.md`'s method and endpoint sections.
5. Tests: `ChecksumApiTest`, `PublicApiControllerTest`, the integration
   `ReachTest`, the sidebar specs.

**Verification:** PHPUnit unit and integration on NC 33 and 34, Vitest,
`npm run typecheck`, ESLint, ECS, Psalm, the build, the e2e `checksums`
spec on NC 34, the OpenAPI file parsing.
**CHANGELOG:** Changed, `GET /api/v1/file/{fileId}/hashes`, its twin and
the three methods: `hashes` keyed by algorithm, `updated_at` on the file;
a caller reading the list breaks.

### Block 2: `ChecksumApi::listHashes()`

1. `listHashes(?array $reachUids, ?string $algo = null, int $limit = 500,
   int $after = 0, ?int $since = null, bool $withLocalPath = false): array`,
   returning `files`, `next` and, without `after`, `estimated_total`.
2. The page query in `MetadataService`: index rows for the hash keys,
   joined to the filecache, inside the reach's mounts, `file_id > after`,
   `updated_at >= since`, ordered by file id, `limit + 1` files.
3. The count for `estimated_total`, the same selection without the page.
4. The values from the documents, one batched read per page; the paths and
   locations from the reach's mounts in one pass per page.
5. Unit tests: the shape, `{}` for no hashes, `next` at the end and before
   it, `limit=0`, `since`, `algo`. Integration tests on a real database: a
   full SHA-256 from the document; a file deleted between two pages skips
   nothing; a share listed for its subtree only; a reset file left out.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS,
Psalm; a page of 500 timed on the harness.
**CHANGELOG:** Added, `ChecksumApi::listHashes()`: every hash in reach,
paged by file id, with `since`.

### Block 3: `GET /api/v1/hashes` and its twin

1. The two routes, `#[UserRateLimit( limit: 300, period: 60 )]` each, the
   twin behind the password confirmation, with `users[]`, `groups[]` and
   `localPath` as settled above.
2. Controller tests: the routes, the scopes, `localPath` for a sudoer with
   a narrowed set and refused for a group admin, the attributes.
3. Docs: `docs/api-v1.md` (the catalogue, the endpoint, the cross-account
   table, the rate limits with the overwrite and the allowlist), the
   OpenAPI file (both paths, the listing schema), the README's REST table.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS,
Psalm, the OpenAPI file parsing, a full listing of the harness's files
through `curl` with an app password, paged to `next: null`.
**CHANGELOG:** the Added bullet names the two routes.
