# AP EtagStamp v1.1: Hashes vouched by ETag

## TL;DR

A hash is valid while its file's ETag is the one it was computed against.
The app keeps that ETag in a stamp row it owns; the API returns it, valid or
`null`, with the file's present size and mtimes, and lists unhashed files.

- `setSelfIndexed()` + `Unchanged` enum → one writer for the app's own
  index rows
- Stamp row: Nextcloud's → the app's, string half = ETag
- ETag: hashing → the one read; adoption → current, on a matching
  `oc_filecache.checksum` entry; import → none
- Legacy: repair `etag-stamp` → ETag by the adoption rules, else queued
- Stale (ETag differs; legacy: `updated_at < storage_mtime`) → left out;
  `StampCheck` erodes and queues, daily
- `?stat=1` (`hashes`, `lookup`, `listHashes`, recalc) → hashes and `etag`
  valid or `null`; `size`, `mtime`, `storageMtime` current; stale entries in
- `GET /api/v1/hashes/missing` → files without hashes; `unmatched`,
  `withIgnored`, `withExcluded`, `stat`; complement of `listHashes?stat=1`

### Blocks

1. `setSelfIndexed()` and `Unchanged`; the app's own index rows through it
2. The stamp row becomes the app's and carries the ETag; repair `etag-stamp`
3. Validity by ETag: stale left out at read; `StampCheck` erodes and queues
4. `?stat=1`: hashes and `etag` valid or `null`; size and mtimes current
5. `GET /api/v1/hashes/missing`, with its flags and `stat`

## Discussion

The requirement comes from kunstarchiv: the ETag the API returns must be the
one the hash was computed against. The current one from `oc_filecache` would
pair a file's new ETag with its old hash after an edit the app did not hear
of - a missed write event, a change on external storage a scan picks up, a
write while the app was disabled - and nothing on the client could tell.

kunstarchiv reads `listHashes` with `since` and `now`, and wants the API to
replace its own full scan of `oc_filecache`: one complete read naming every
file of an account with its present state. Its review of v1.0 asked for what
v1.1 adds - the fields of a stale entry, `storageMtime` everywhere, and the
missing route as the other half of that read.

Decided in the evaluation, with what was rejected:

- **The ETag lives in the stamp row's string half**, the row taken over from
  Nextcloud. `pageListedFiles()` is driven by that row, so the listing reads
  the ETag with no extra join. A key of its own was rejected for that join.
  The document keeps the ETag too, in an unindexed `file-checksum-etag`, so
  the single-file route reads it and a repair can rebuild the row.
- **Evidence and state are apart.** A file's hashes and its `etag` are the
  evidence: valid together, or `null` together, never a `stale: true`
  beside old values. `size`, `mtime` and `storageMtime` are the file's
  present state, from the filecache, on every entry under `stat=1`; so are
  `fileid`, `path` and `owner`. v1.0 nulled size and mtime with the hash,
  which would have sent a consumer back to the filecache for them.
- **A stale hash stays in the system.** It is left out by default, as stale
  hashes are today, and included under `stat=1`.
- **Hashes of algorithms no rule names are still dropped on a write**
  (0.22.0). One stamp and one ETag vouch for all of a file's hashes; a hash
  the queue never recomputes would sit beside the new stamp and ETag and
  read as valid. An ETag per hash was rejected: both halves of a hash row
  are taken, the truncated value and the write time `since` reads.
- **Trust is Nextcloud's.** Adoption takes the current ETag where the
  filecache's checksum collection holds the same value: Nextcloud clears
  that column whenever its scanner sees a change. A legacy hash without an
  ETag is valid while `updated_at >= storage_mtime`; a client-set mtime
  reaches `storage_mtime` through `touch()`, as it reaches a `stat()` of the
  file, and is trusted as Nextcloud trusts it. Content replaced by a client
  that keeps an older mtime passes that test with the old hash; the hole
  closes for each file when `etag-stamp` converts it, and the README says
  so. A rule flag that trusts nothing from outside is for later.
- **Two listings, one inventory.** `listHashes` lists the files with hash
  rows; `/hashes/missing` the files with none. Under `stat=1`, with every
  flag on the missing route, they are complements: a file of the files area
  in neither is gone. Trash, versions and app data are in neither.
- **`Unchanged` is an enum**, not a singleton class: an enum case is a
  constant expression, so it can be a parameter default and a class
  constant; an object can be neither.
- **The missing files get a route of their own** rather than a mode of
  `listHashes`: one query and one set of parameters per route, no `since`
  to refuse and no `estimated_total` to leave out.
- **Times:** `mtime` and `storageMtime` in ISO 8601 UTC with whole seconds
  and an explicit offset, as `updated_at` is, so a consumer converts them
  back to seconds exactly. `since` and `now` stay Unix seconds.
- **The daily check:** `RuleProcessingJob` queues a `StampCheck` walk once
  per `stamp_check_interval` (default one day), so the walk stays one job
  with one cursor, as the `missing-stamps` repair already uses it.

## Analysis

What the plan rests on, checked against the code and Nextcloud 34:

- **Nextcloud rewrites only indexed keys' rows.**
  `FilesMetadataManager::saveMetadata()` drops and reinserts the rows of
  the keys a document flags indexed (`IndexRequestService::updateIndex()`),
  and leaves every other row alone; rows go only with the file's metadata.
- **The flag lives in each document**, not only in the key's registration.
  Until a file's document is rewritten unindexed, another app's save of it
  has Nextcloud rebuild the stamp row from the document, and the ETag in
  the row is lost. The repair step therefore rewrites every stamped
  document; until it has, `StampCheck` restores the row from the document.
- **The stamp is set in 11 places**, each `setInt(UPDATED_AT…, true)`:
  `HashCalculationService` 843, 876, 1353; `MetadataService` 530, 1187,
  1222, 2492, 2496, 3304, 4236, 5016. Two more insert the row directly
  (`MetadataService` 2161, 3286). All go through one `stamp()`.
- **The ETag is in hand while hashing:** `HashCalculationService` reads it
  before the read (1305, 1699) and compares `etagOf()` after (1319, 1701).
- **The app already keeps rows of its own:** `syncHashIndex()` for the
  hashes, the state rows for markers, and the MIME type row, all through
  the private `insertIndexRow()`.
- **`oc_filecache.checksum` is a collection**, `ALGO:value` pairs; the
  `missing-stamps` repair already compares a hash with its algorithm's
  entry. Nextcloud clears the column whenever the scanner sees a change
  (`Scanner.php:216`), and a WebDAV upload sets it from the client's header
  or clears it.
- **`storage_mtime` is in seconds**, the storage's own `stat()` mtime.
- **What each route reads today:** `lookup` → `queryByHash()`, joined to
  the filecache, then `batchLookupFilecachePaths()`; `listHashes` →
  `pageListedFiles()`, stamp row `u` and filecache `fc` joined; `hashes` →
  `getHashesByFileId()`, no filecache row; recalc → `recalcHash()`,
  `recalcMany()`. The read-time check is a comparison in queries that
  already hold both values, a stamp-row join for `lookup`, and one
  primary-key read for `hashes` and recalc. The present-state fields come
  from the same filecache rows.
- **What makes the listings complements:** `whereListed()` keeps a file
  with at least one hash row and, today, no stale state. Under `stat=1` the
  stale condition becomes a returned column; the missing route takes the
  files with no hash row at all. A queued file never hashed has a stamp row
  of 0 and no hash row, so it is missing, not listed.
- **Rule verdicts are decided in PHP**: `andWhereGoverned()` only keeps a
  query to the files area. The missing route filters each page after its
  query, so a page can come back short and always carries `next`.
- **The repair precedent:** `missing-stamps` is an expensive step; a whole
  repair queues `StampCheck`, and a named run (`--step`) or
  `--include-expensive` runs it to completion at once.
- **Texts:** no new user-facing text is expected. A repair step's title and
  output are console English. Should one appear, `scripts/l10n.sh update`
  and every kept language come with it.

Not in scope: `stat` on the duplicates listings and the CLI's JSON; the rule
flag that trusts nothing from outside; an ETag per hash; deletions reported
under `since`; moving `Unchanged` to mwx/lib.

## Implementation Plan

### Block 1: `setSelfIndexed()` and `Unchanged`

1. `lib/State/Unchanged.php` (or beside `MetadataService`): `enum Unchanged
   { case Unchanged; }`.
2. `MetadataService::setSelfIndexed(int $fileId, string $key,
   Unchanged|string|null $string = Unchanged::Unchanged,
   Unchanged|int|null $int = Unchanged::Unchanged)`: upserts the key's one
   row, the string truncated by `truncateForIndex()`, a half left as it is
   where `Unchanged`, NULL where `null`. `unsetSelfIndexed()` deletes it.
   The document is the caller's, in the same save.
3. `syncHashIndex()`, the state rows and the MIME type row write through it;
   `insertIndexRow()` stays private beneath it.
4. CHANGELOG, Changed (draft):
   `- MetadataService::setSelfIndexed(): one writer for the index rows the`
   `  app keeps itself, truncated to 63 characters in one place.`

**Verification:** unit tests for the halves (`Unchanged`, `null`, a value),
truncation at 63 and the delete; the unit and integration suites on 33 and
34 unchanged in outcome; `composer cs:check`, `composer psalm`,
`changelog.sh check`.

### Block 2: The stamp row becomes the app's

1. `file-checksum-updated_at` registered unindexed (the `metadata-keys`
   step), and `file-checksum-etag`, unindexed, beside it.
2. `MetadataService::stamp(int $fileId, IFilesMetadata $metadata, int
   $time, ?string $etag)`: the document's two keys, then the row through
   `setSelfIndexed()`. The 11 call sites and the two direct inserts use it;
   a queued or reset file is stamped 0 with no ETag.
3. Hashing: the ETag read before the read, where `etagOf()` still returns
   it after.
4. Adoption (the filecache copy, `missing-stamps`,
   `rebuild-from-filecache`): the current ETag, where the hash equals its
   algorithm's entry in `oc_filecache.checksum`; otherwise none.
   `ImportService`: none.
5. Repair step `etag-stamp`, expensive: rewrites each stamped document with
   the key unindexed, and gives a hash without an ETag one by the adoption
   rules - its entry in `oc_filecache.checksum`, else
   `updated_at >= storage_mtime` - or queues the file. A whole repair queues
   it for the background, as `missing-stamps` does; `occ fcias:repair
   --step etag-stamp` runs it at once.
6. `StampCheck`: compares each stamp row with its document and restores
   the row from it.
7. README *Repair Commands*: the step.
8. CHANGELOG, Changed (draft):
   `- README.md, *Repair Commands*, etag-stamp: a file's stamp carries the`
   `  ETag its hashes were computed against.`

**Verification:** integration: hashing stores the ETag read; an edit during
the read stores none; adoption takes the current ETag only on a matching
entry; another app's metadata save leaves the row's ETag in place; the
repair step converts a legacy file, queues one that fails, and runs again
with nothing to do; `StampCheck` restores a row wiped by hand. Both suites
on 33 and 34, lint, `changelog.sh check`.

### Block 3: Validity by ETag

1. One SQL condition, valid: stamp row ETag = `fc.etag`, or no ETag and
   stamp `>= fc.storage_mtime`. `lookup`, `listHashes`, `hashes` and the
   recalc answers leave a file failing it out, as a stale file is today.
2. `StampCheck` walks the stamp rows against the filecache and, for a file
   failing it, does what a missed write would have done: marks its hashes
   eroded and queues it.
3. `RuleProcessingJob` queues a `StampCheck` walk once per
   `stamp_check_interval` (lexicon, default 86400).
4. README *When hashes go away*: a change the app did not hear of, and the
   legacy test's trust in a client-set mtime until `etag-stamp` has run.
5. CHANGELOG, Fixed (draft):
   `- README.md, *When hashes go away*: a file changed without the app`
   `  hearing of it has stale hashes, and is queued again.`

**Verification:** integration: a filecache ETag changed by hand hides the
file from `lookup`, `listHashes` and `hashes`; the walk erodes and queues
it; the drain makes it valid again; a legacy file passes and fails the
mtime test. Both suites on 33 and 34, lint, `changelog.sh check`.

### Block 4: `?stat=1`

1. `ChecksumApi`: `$withStat` on `getHashesByFileId()`, `findByHash()`,
   `listHashes()`, `iterateHashes()`, `recalcHash()`, `recalcMany()`;
   the routes and their `/sudo/` twins take `stat`.
2. Each file gains `etag`, from the stamp row, valid or `null` with its
   hashes; and `size`, `mtime` and `storageMtime`, the file's present state
   from the filecache, on every entry. Times in ISO 8601 UTC, whole seconds,
   explicit offset. A stale entry is included, with `fileid`, `path`,
   `owner` and the present-state fields, its hashes and `etag` `null`.
3. `docs/api-v1.md` and `docs/api-v1-openapi.yaml`: the fields, the
   evidence-and-state split, and the inventory the two listings make.
4. CHANGELOG, Added (draft):
   `- docs/api-v1.md, ?stat=1: a file's etag, valid for its hashes or null,`
   `  and its present size, mtime and storageMtime.`

**Verification:** controller and integration tests per route and twin:
the fields; a stale entry with its hashes and `etag` `null` and its
present-state fields set; nothing new without `stat`; `storageMtime` with
and without `localPath`; the recalc answer carrying the new ETag. Both
suites on 33 and 34, lint, `changelog.sh check`.

### Block 5: `GET /api/v1/hashes/missing`

1. `ChecksumApi::listMissing(?array $reachUids, ?string $algo, int $limit,
   int $after, bool $unmatched, bool $withIgnored, bool $withExcluded,
   bool $withStat)` and the route with its `/sudo/` twin: files in reach
   with no hash row (with `algo`, none of that one), paged over
   `oc_filecache` by file id, files only, under a scan budget; `next` and
   `now` on every page.
2. By default the files an include rule governs; `unmatched=1` adds those
   no rule matches, `withIgnored=1` those an `ignore` rule matches,
   `withExcluded=1` those an `exclude` rule matches.
3. Each file: `fileid`, `path`, `owner`, `location`; under `stat=1`,
   `etag` `null` and the present-state fields, as Block 4.
4. `docs/api-v1.md`, `docs/api-v1-openapi.yaml`, `#[UserRateLimit]` as the
   listing has.
5. CHANGELOG, Added (draft):
   `- GET /api/v1/hashes/missing: the files without hashes, governed ones by`
   `  default; with listHashes?stat=1, every file in reach.`

**Verification:** integration: governed, unmatched, ignored and excluded
files under each flag; `algo`; a short page carrying `next`; `now` on each
page; reach for the twin; and the complement: over a fixture account,
`listHashes?stat=1` and `/missing` with every flag name each file of the
files area exactly once. Both suites on 33 and 34, lint,
`changelog.sh check`.
