# AP SudoMode v1.0: an admin is a user until they say otherwise

> **Status: proposed 2026-09-03, awaiting EXEC.** Follows the two `[SECURITY]`
> fixes 3b18858 and 34f12e4, which closed findings F1 and F2 of the security
> analysis in `wip/`. This is the third piece the analysis's F1 raises and the
> only one that changes what administrators can do.

## Problem

`PublicApiController::resolveRequestingUserScope()` answers `null` for an
administrator, and `null` means unrestricted. Four endpoints read it — the
per-file hashes, the per-file duplicates, the hash lookup and the
recalculation — so an administrator browsing their own files is, without
choosing to be, reading across every account on the instance. The Duplicates
page's `?user=` parameter is the same thing by another route.

Nothing about that is an accident, and nothing about it is visible. An
administrator has no way to work as themselves, and no moment where the
instance-wide view is a decision they took.

## Decision

**An administrator is an ordinary user of their own files until they say
otherwise, and saying otherwise costs a password.**

- `resolveRequestingUserScope()` answers the caller's own uid for everyone.
  The unrestricted answer stops being a property of who you are.
- The instance-wide view becomes an explicit route rather than a mode of the
  existing one, because Nextcloud's `#[PasswordConfirmationRequired]` is a
  per-method attribute and putting it on a shared method would prompt for a
  password on every ordinary read.
- Those routes are administrator-only, carry the attribute, and are the only
  ones that pass `null` down. Core's middleware holds a confirmation for 30
  minutes, which is the sudo window.
- The Duplicates page gains a **Show all users** switch, visible only to an
  administrator. Turning it on runs the password confirmation and then reads
  the instance-wide route; turning it off returns to their own files. The
  switch does not persist: a reload is back to normal mode.

## Scope

Backend: `PublicApiController` (scope resolution, one new route per endpoint
that needs one), `DuplicatesController` (the `?user=` path moves behind the
same gate), route registration, `#[PasswordConfirmationRequired]`.

Frontend: `src/duplicates-vue/App.vue` (the switch), a small helper wrapping
`OCS` password confirmation, `src/routes.ts`.

Docs: `docs/api-v1.md` and the OpenAPI spec (new routes, and the changed
meaning of the existing ones for administrators), `README.md`,
`docs/user-guide.md`, `docs/FAQ.md`, CHANGELOG.

Tests: controller tests for both scopes, a unit test that an administrator
without confirmation is refused, e2e for the switch.

## Open decisions — please rule before EXEC

1. **This is a breaking change for administrator API clients.** A script
   calling `/api/v1/lookup` or `/api/v1/duplicates` with administrator
   credentials today gets instance-wide answers and would get its own files
   instead. Password confirmation is session-based, so such a client cannot
   simply opt in — it would need the new routes and an interactive
   confirmation it cannot perform. Three ways out:
   a. Accept it. The app is pre-1.0 and the current behaviour is the finding.
   b. Keep the existing routes unrestricted for administrators and gate only
      the new UI surface. Honest about compatibility, dishonest about the
      problem: the oracle stays open to any administrator's API token.
   c. Gate by session type: an interactive session is scoped and must
      confirm; a token/Basic-auth call keeps today's behaviour. Preserves
      scripts, but "who you are" still decides for non-interactive callers.
   My recommendation is (a), stated in the CHANGELOG under Security with the
   migration note for anyone scripting against it.
2. **Does the sidebar's per-file view need the same?** A file an
   administrator cannot reach through their own folder currently answers its
   hashes. Under this AP it stops. That is the same fix as F1, one endpoint
   over, and I would include it — say if not.
