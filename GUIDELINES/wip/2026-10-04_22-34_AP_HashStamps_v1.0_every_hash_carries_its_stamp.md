# AP HashStamps v1.0: every hash carries its stamp

## Discussion

Settled with the user, 2026-10-04:

- **`file-checksum-updated_at` is a must** for every file that holds a
  hash. Its int half is the stamp: until when the hashes are held current.
  Its string half is the queue's marker (`pending:<mode>`, `stale:…`).
- **Outdated hashes are worse than none.** After a content change, every
  hash is either recomputed or dropped.
- **`auto` keeps only what its rule names.** A hash computed once by hand
  (the sidebar) is not recomputed on every change; whoever needs it
  regularly writes a rule.
- **A hash is current only while its index row exists.** A content change
  deletes the file's hash rows at once and sets the stamp to 0 in the
  metadata document; the recomputation writes them back. The metadata
  document keeps the old hashes until then, so `auto` still knows which
  algorithms the file had.
- **The marker is a hint, the stamp is the proof.** Nextcloud rewrites the
  stamp's index row from the document on every metadata save, by any app,
  and leaves its string half empty. So a write sets the stamp to 0 in the
  document; the marker alone can be lost.
- **Decisions:**
  - one plan, four blocks; the write time per hash row (block 4) waits for
    AP ListingPerformance, which rebuilds the same query;
  - hashes nobody vouches for (a stamp of 0) stay hidden until recomputed;
  - the repair stamps a file's mtime where the filecache still holds the
    same hashes, 0 elsewhere;
  - recalculating a queued or outdated file on demand processes it as the
    queue would, plus whatever was asked.

## Analysis

- **Why stamps are missing.** `HashCalculationService::recalcHashes()`
  writes and saves hashes but never sets the stamp; only `processFile()`
  (the queue) does, after it. Every other caller leaves files unstamped:
  `occ fcias:hash` (`generateMissingHashes()`), the REST, sidebar and
  `ChecksumApi` recalculation (`recalcFileHash()`, `recalcHash()`),
  `recalcAllExistingAlgos()`.
- **What it breaks.** A file without a stamp counts as never hashed, so
  every `missing` run hashes it again; a reset does not mark it; the
  index check does not see it; the listing shows `updated_at: null`.
- **Measured on helioscloud.ddev.site, read-only:** 25,906 files, all
  Kunstarchiv's, sha1 and sha256 each, no stamp in the document either,
  saved by one `occ fcias:hash --user=kunstarchiv` run on 2026-10-01
  between 09:57 and 10:53 UTC. For each, the filecache still holds the
  same hashes and the mtime predates the save.
- **The md5 case.** A write under an `auto` rule keeps the hashes and
  queues the file; `processFile()` recomputes the rule's algorithms the
  document holds and stamps the whole document. Any other hash — one
  computed by hand — still describes the old content and is now vouched
  for. `syncHashIndex()` rebuilds the rows from every hash in the
  document, so its row comes back too. `missing` has the same gap.
- **Sync clients keep mtimes.** An upload of a file edited offline carries
  the client's mtime, which can be older than the stamp: `stamp < mtime`
  then misses the change, and `recalcHashes()` returns the old hash as
  current. A write therefore invalidates explicitly.
- **Where the write invalidates.** In `FileListener::onWrite()`, at the
  cost of one metadata save per write of a file with hashes, not in a
  `MetadataLiveEvent` listener: Nextcloud raises that event for every
  metadata refresh, `occ files:scan --generate-metadata` included, which
  would set every stamp on the instance to 0.
- **A write during the read.** A recomputation stamps the time taken
  before it reads, and compares the file's etag before and after: a write
  that lands mid-read discards the result, as a locked file does, and the
  file stays queued.
- **Changes the write listener does not see** — a scan finding a file
  changed on disk or on external storage — reach the rule sweep as
  `stamp < mtime`; the sweep deletes their hash rows when it queues them.
- **Repairs.** `rebuild-from-metadata` and `unindexed-hashes` rebuild rows
  from metadata documents; they skip a document whose stamp is not current
  or whose marker is `pending:` or `stale:`.
- **Imports.** `--allow-stale` stores a stamp older than the file; such a
  file is outdated by its own stamp, and gets no rows.

## Implementation Plan

### Block 1: a recalculation stamps what it saves

1. `recalcHashes()` stamps the time taken before the read whenever it
   saves computed hashes, and compares the file's etag before and after the
   read: a change discards the result and reports the file as busy
   (`locked`).
2. `recalcHashes()` on a document it loaded itself (every on-demand
   caller), when the document is outdated — no stamp, 0, older than the
   mtime, or a `pending:` marker: computes the algorithms the queue would
   for the file's mode and rule, plus the ones asked, in one read, and
   drops every other hash from the document.
3. `processFile()`: before it computes, drops from the document every hash
   its mode and rule do not cover (`auto`: the rule's algorithms the file
   had; `missing`: the rule's); no include rule and an outdated document:
   the hashes are eroded, as `onWrite()` does for a file no rule maintains.
4. Tests, unit and integration: `occ fcias:hash` and `recalcFileHash()`
   leave a stamp; the md5 case; an on-demand recalculation of a queued
   file; a change during the read.

**Verification:** PHPUnit unit and integration on NC 33 and 34, ECS,
Psalm.
**CHANGELOG:** a Fixed bullet.

### Block 2: files with hashes and no stamp get one, in the background

1. `MetadataService`: the files whose index holds a hash row and no stamp
   row, a keyset page at a time; stamping one: the file's mtime where the
   filecache's checksum still holds every hash of its document, otherwise
   0, its hash rows deleted and the file queued (`pending:auto`); written
   to the metadata document, so Nextcloud writes the stamp row.
2. A queued background job, `StampCheck`, in slices of 30 seconds with its
   place kept, like `HashIndexCheck`; its run on the status page and in
   `occ fcias:status`.
3. A repair step, `missing-stamps`: a whole repair queues the job, naming
   it runs it at once.
4. `unindexed-hashes`: a document without a stamp gets one by the same
   rule, in the document rather than as an index row only.
5. Tests: the stamp from the mtime, the 0 and the queue where the
   filecache disagrees, a document already stamped, the job's slices, the
   repair step queuing and running.
6. Documents: `README.md` and `docs/FAQ.md` name the step.
7. Measure the page query on helioscloud.ddev.site, read-only.

**Verification:** as block 1; `scripts/l10n.sh check` for the status
page's labels.
**CHANGELOG:** a Fixed bullet.

### Block 3: a content change hides the file's hashes until they are recomputed

1. `FileListener::onWrite()`, for a file whose document holds a hash under
   an `auto` or `missing` rule: the stamp set to 0 in the document, the hash
   rows deleted, the file queued with the rule's mode. `force`, `lazy` and
   a file no rule maintains keep their current handling, which already
   clears.
2. The rule sweep and `applyRule()`: a file queued because its stamp is
   older than its mtime loses its hash rows.
3. `syncHashIndex()` is reached through one guard: rows only for a
   document whose stamp is current.
4. `rebuild-from-metadata` and `unindexed-hashes` skip a document that is
   not current or carries a `pending:` or `stale:` marker.
5. `ChecksumApi::getHashesByFileId()` — and with it the sidebar and the
   per-file routes — returns only hashes with an index row.
6. Tests: a write under `auto` and under `missing` hides the hashes from
   the lookup, the listing and the per-file route until the queue runs; an
   upload whose mtime is older than the stamp; the sweep; the repairs
   leave an outdated document's rows out.
7. Documents: `docs/api-v1.md` on what a file's hashes are between a change
   and its recomputation.

**Verification:** as block 1.
**CHANGELOG:** a Fixed bullet.

### Block 4: each hash row carries when it was written (after AP ListingPerformance)

1. A hash row's int half holds the time its value was written to this
   instance; `syncHashIndex()` writes only the rows that change, so an
   unchanged row keeps its time.
2. `since`, on `GET /api/v1/hashes` and `ChecksumApi::listHashes()` and
   `iterateHashes()`, keeps the files with a hash row written at or after
   it: a feed of hashes added or changed, still not of moves, renames or
   deletions.
3. Rows written before hold 0, before the feed began.
4. Tests and `docs/api-v1.md`.

**Verification:** as block 1.
**CHANGELOG:** the Added bullet for `GET /api/v1/hashes`, amended.
