# /plan — Create Action Plan

Produces a structured Action Plan (AP) from the instructions in the command body, persists it as a UAMF, and presents it as a gate message. Does NOT execute code — execution is gated behind `EXEC`-family signals.

## 1. Core Rules (MUST)

| Rule  | Source |
|---|---|
| Non-trivial CODE tasks require an AP | [`AGENTS.md`](AGENTS.md) §1.2 |
| Persist AP as UAMF **before** any project writes | [`AGENTS.md`](AGENTS.md) §1.2, §5.3 |
| Each AP revision creates a **new** UAMF file with a fresh timestamp — never overwrite | AGENTS.md §4, §5.3 |
| Present AP summary as a gate message unless `EXEC` is inline | [`AGENTS.md`](AGENTS.md) §1.2, §3.1 |
| Gate follows Universal Gate Template | [`AGENTS.md`](AGENTS.md) §1.1 |
| Do NOT execute code from this, unless for investigation and the command has no side-effect | This command is planning-only |

## 2. AP Format (MUST)

Per [`AGENTS.md`](AGENTS.md) §5.1–5.2:

### 2.1 Title

```
AP {topic} v{Major}.{Minor}: {2-5 word description}
```

- `{topic}`: 1–3 word PascalCase subject descriptor (e.g. `Bild`, `Objekt`, `DecisionEngine`, `CliRefactor`)
- `{topic}` is **not** a workflow signal — `PLAN`, `EXEC`, `ASK`, `ROLLBACK`, `ERR` are user-facing keywords, not AP title components
- `{Major}.{Minor}`: increment Minor on revisions within same session; Major for structural redesigns
- Examples: `AP Bild v1.0: Extract decision functions`, `AP FilterFix v1.0: Fix type validation`

### 2.2 Required Sections

1. **Discussion** — context, design trade-offs, rejected alternatives (only if they clarify the final choice)
2. **Analysis** — what needs to change, scope boundaries, impact assessment, what's NOT in scope
3. **Implementation Plan** — step-by-step blocks, each with a **Verification** checkpoint
4. **Proposed commit message** — follows [`AGENTS.md`](AGENTS.md) §6 (summary prefix + body)
5. **Change History** — append-only table; first row is `v1.0, date, Initial AP`

### 2.3 Persistence (UAMF)

Write to `.aiassistant/messages/YYYY-MM-DD_HH-NN_AP_{topic}_v{M}.{m}_{description}.md`.

Example: `.aiassistant/messages/2026-06-15_12-10_AP_Registry_v1.0_bild_static_registry.md`

## 3. Workflow

### 3.1 Step 1: Understand the Task

- Read the command body — it contains the task description and any constraints
- Include an explicit to-do list point "Read `/plan` command`" marked as checked if your read this file
- If command body is extensive (>10 lines), it is most likely generated by an Orchestator task or resuming a previous failed task. Ask user for immediate last-minute amendments similar to step 4 (see §3.4 Present preliminary findings).
- Check [`ROADMAP.md`](ROADMAP.md) if the task relates to architectural priorities
- Read relevant source files to understand current state
- Do NOT read files blocked by [`.rooignore`](.rooignore)

### 3.2 Step 2: Scope the AP

- Identify the bounded scope: what's in, what's out
- Check for existing tests and mock infrastructure that can be reused
- Consider test isolation needs (see [`.aiassistant/TESTING.md`](.aiassistant/TESTING.md))
- Identify which ROADMAP.md priority this addresses (if any)

### 3.3 Step 3: Structure the Implementation Plan

- Break into numbered blocks with clear boundaries
- Each block ends with a **Verification** checkpoint (e.g. "tests pass", "no deprecations")
- Order blocks so each builds on the previous
- Identify potential side effects or cross-cutting concerns

### 3.4 Step 4: Present preliminary findings
- MANDATORY: The message body MUST contain the full analysis (scope, files, alternatives, risks).
  The question parameter is ONLY "Any feedback before writing full AP?"
  Do NOT write the analysis in thinking and summarize in body. INVERT THIS.
- Follow §3.6.1 on how to use the `ask_followup_question` tool
- Use the `ask_followup_question` tool to present a *brief* analysis in a gate message
- Use the `question` parameter to present the analysis and ask "Any feedback or shall I continue?"
- Use the `follow_up` parameter to offer to continue with creating and persisting the full AP as per next step
- If the user answers with additional comments that don't include `/EXEC` or an equivalent instruction, update your analysis and present them again in a new gate message before writing the AP. Only proceed to write the AP once you receive a clear `/EXEC` or equivalent instruction.

### 3.5 Step 5: Write the AP UAMF

- CRITICAL CHECK (MUST pass before ANY file write): \
Is the target file in .aiassistant/messages/ ?
  - → If YES: STOP. Create a NEW file with fresh timestamp + incremented version.
  - → NEVER use apply_diff on UAMF files.
- Write the AP file to `.aiassistant/messages/` with proper timestamp and filename
- Include ALL required sections (§2.2)
- Propose a commit message following [`AGENTS.md`](AGENTS.md) §6
- Open created UMAF in IDE using MCP server jetbrains's open_file_in_editor tool.

### 3.6 Step 6: Present Gate Message

Follow the Universal Gate Template ([`AGENTS.md`](AGENTS.md) §1.1):

```
Checkpoint: {AP title}
Overall Task: {one-line summary}
Last Action: Created AP at {UAMF path}
Pending action: {numbered blocks from Implementation Plan}
Confirmation needed: EXEC / EXEC+ / EXEC++ / EXEC+++ / ROLLBACK
```

#### 3.6.1 Delivery Mechanism (STRICT)

**Delivery mechanism (STRICT):** Use the native tool `ask_followup_question`. Write the gate message in the `question` parameter of `ask_followup_question` **ending with a short call-to-action label**.

- **Tool**: Use the native tool`ask_followup_question`
- **`question` parameter**: Full gate summary in Markdown (Checkpoint, Overall Task, Last Action, Pending action, Proposed commit message, Changelog, Files to be committed). Write this exactly as you would any other response body. Ending on a single short line: `"Confirmation needed: EXEC / EXEC+ / EXEC++ / EXEC+++ / ROLLBACK"`.
- **`follow_up` parameter**: User choice buttons with mode switches where appropriate.

Using `ask_followup_question` instead of `attempt_completion` is semantically correct — a gate is a question awaiting confirmation, not a "task completed" signal.

**Format:**

```
message body: (full gate in Markdown — Checkpoint, Overall Task, Last Action, Pending action)

question: "Confirmation needed: EXEC / EXEC+ / ROLLBACK / REFINE"

follow_up: [
  { text: "/EXEC — Implement all blocks now", mode: "code" },
  { text: "/EXEC + — Implement + commit afterward", mode: "code" },
  { text: "ROLLBACK — Abandon this plan", mode: null },
  { text: "REFINE — I have feedback to revise", mode: null }
]
```

The `mode` field on `/EXEC` and `/EXEC +` options switches to `code` mode automatically when selected. `ROLLBACK` and `REFINE` keep the current mode.

## 4. Revision Handling

| Trigger | Action |
|---|---|
| User feedback (no signal) | Revise AP → write new UAMF → increment Minor version → present updated gate |
| User says `ROLLBACK` | Abandon current AP version; ask if reverting to previous version or starting fresh |
| User says `PLAN` again | Treat as revision request; apply feedback to next version |
| Scope change via user message | Update AP, increment version, note change in Change History |

## 5. Commit Message Format

Per [`AGENTS.md`](AGENTS.md) §6:

```
[{TAG}] {Brief summary}

{Detailed body explaining what and why}

{Optional: key changes, test results}
```

Valid tags: `[TASK]`, `[FIX]`, `[SECURITY]`, `[CLEANUP]`, `[WIP]`, `[UPDATE]`

## 6. Edge Cases

| Scenario | Action |
|---|---|
| Task is trivial (single-line fix) | Note that AP may not be needed; ask user to confirm if they want to skip |
| Task spans multiple ROADMAP priorities | Note which priorities are addressed; identify which are deferred |
| Existing tests need changes | Include test-update blocks in Implementation Plan |
| New mocks needed | Include mock creation in Implementation Plan |
| User provides EXEC signal in same message | Execute only if explicitly combined (e.g. `/plan EXEC`); otherwise gate |
| No `.aiassistant/messages/` directory | Create it |
| Task references files outside workspace | Note limitation; ask for clarification |
